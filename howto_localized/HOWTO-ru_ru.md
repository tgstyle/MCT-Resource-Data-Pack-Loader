# Resource Data Pack Loader

**Одна папка. Переопределяет всё, что даёт Minecraft или мод, описывает новый контент в JSON и управляет генерацией мира.**

Два готовых примера. Положите любой прямо в `rdploader` и посмотрите, как написан каждый файл.

- [RDPLExamplePack.zip](https://github.com/tgstyle/MCT-Resource-Data-Pack-Loader/raw/refs/heads/1.12.2-1.0-Release/example/RDPLExamplePack.zip) покрывает большинство возможностей: блоки, предметы, биомы, измерение, шаблон мира и все формы генерации.
- [RDPLExampleOrePackVoid.zip](https://github.com/tgstyle/MCT-Resource-Data-Pack-Loader/raw/refs/heads/1.12.2-1.0-Release/example/RDPLExampleOrePackVoid.zip) превращает обычный мир в пустоту, где генерация висит в воздухе по одной форме на полосу высоты — так каждую видно отдельно.

# С чего начать

## Что это

Resource Data Pack Loader (RDPL) добавляет в сборку одну папку: `rdploader`. У неё три задачи.

**Переопределение.** Кладёте файл — и он заменяет тот, который взяли бы игра или мод. Никаких переключателей, никакой настройки для каждого мира, ничего, что игроку надо включать в меню. Если файл лежит в папке, именно его игра и загрузит.

**Новый контент.** Добавляете JSON-файл с описанием блока, предмета, жидкости, биома, измерения, зелья или жителя — и он регистрируется. Без Java, без jar.

**Управление.** Запретить генерацию руды, биомов, структур или рецептов, выровнять бедрок, задать частоту спавна или превратить обычный мир в пустоту.

## Как писать JSON

Все файлы здесь — JSON. Вот один, настоящая запись генерации мира, и в нём встречаются все формы, какие в JSON бывают:

```json
{
  "blocks": [
    { "block": "minecraft:wool", "weight": 80, "properties": { "color": "magenta" } },
    { "block": "mypack:ruby_ore", "weight": 20 }
  ],
  "size": { "min": 4, "max": 12 },
  "attempts": 12,
  "maxTemperature": 0.5,
  "sparse": true,
  "replace": ["minecraft:stone", "minecraft:andesite"],
  "dimensions": [0, -1]
}
```

Разберём построчно:

- Весь файл — один **объект**: открывается `{` в первой строке, закрывается `}` в последней и содержит пары `"ключ": значение` с запятой после каждой пары, кроме последней.
- `"attempts": 12` — **число**, пишется без кавычек. `"maxTemperature": 0.5` — то же самое, с дробной частью.
- `"sparse": true` — **логическое значение**, `true` или `false`, тоже без кавычек.
- `"block": "minecraft:wool"` — **текст**, всегда в двойных кавычках.
- `"dimensions": [0, -1]` — **список**, квадратные скобки, запятые между элементами. В этом лежат числа.
- `"replace": ["minecraft:stone", "minecraft:andesite"]` — список такой же формы, но с текстом, поэтому каждый элемент в кавычках.
- `"size": { "min": 4, "max": 12 }` — **объект как значение**: фигурные скобки вложены в скобки самого файла.
- `"blocks": [ { ... }, { ... } ]` — **список объектов**: фигурные скобки внутри квадратных, запятая между двумя объектами, и у каждого объекта свои пары. `"properties"` внутри первого — это объект внутри объекта внутри списка, и вложенность идёт настолько глубоко, насколько просит таблица.

Те же пять форм таблицей:

| Форма | Как пишется | Пример |
| --- | --- | --- |
| текст (строка) | всегда в двойных кавычках | `"minecraft:stone"` |
| число | без кавычек | `8`, `-1`, `0.5` |
| true или false (логическое) | без кавычек | `true` |
| список (массив) | квадратные скобки, элементы через запятую | `[0, -1]` |
| объект | фигурные скобки с парами `"ключ": значение` через запятую | `{ "min": 4, "max": 12 }` |

Правила, из-за которых файл ломается, если про них забыть:

- Ключи всегда в двойных кавычках. Значения — только когда это текст: `"8"` — текст, а `8` — число, и ключ, ожидающий число, текстовую форму не примет.
- Запятые ставятся между элементами и никогда после последнего. Запятая после последнего элемента — самая частая причина сломанного файла.
- В списке лежат элементы одного вида, и таблицы говорят какого: список целых — `[0, -1]`, список имён блоков — `["minecraft:stone", "minecraft:andesite"]`, а списку из одного элемента скобки всё равно нужны: `[0]`.
- Объекты вкладываются и в объекты, и в списки, так что значение может быть глубиной хоть `"shape": { "type": "cluster" }`, хоть списком объектов вроде `[{ "block": "minecraft:wool", "weight": 80 }]`.

**Как читать таблицы.** В каждой таблице сказано, обязателен ли ключ, что в нём может лежать и что будет, если его не писать. Незнакомое разборщику значение попадает в лог и заменяется значением по умолчанию, а не роняет игру. Что означают слова в колонке значений, и что именно вы пишете:

| Если в таблице написано | Вы пишете |
| --- | --- |
| int | `8` |
| int, тики | `100`, двадцать тиков в секунду |
| int или диапазон | `8` либо `{ "min": 4, "max": 12 }`, чтобы бросать между ними |
| от 0 до 15, от 1 до 100 и подобное | целое в этих границах |
| float | `0.5` |
| boolean | `true` или `false` |
| строка | `"слова в кавычках"` |
| имя блока, имя предмета | `"minecraft:stone"`, с метаданными третьей частью: `"minecraft:stone:3"` |
| `namespace:name` | `"mypack:ruby_ore"` |
| имя биома, имя звука, имя вкладки | та же форма `namespace:name` в кавычках |
| hex-цвет | шесть шестнадцатеричных цифр, `"A0C8FF"`, с ведущей `#` или без |
| путь к текстуре | `"mypack:blocks/ruby_ore"` |
| список целых | `[0, -1]` |
| список имён блоков | `["minecraft:stone", "minecraft:andesite"]` |
| список имён биомов | `["minecraft:extreme_hills", "mypack:ruby_hills"]` |
| список типов словаря биомов | `["MOUNTAIN", "FOREST"]` |
| список id модов или пространств имён паков | `["quark", "mypack"]` |
| список объектов | `[{ "potion": "minecraft:strength", "amplifier": 1 }]`, ключи каждого объекта заданы его собственной таблицей |
| объект | `{ "type": "cluster" }`, ключи заданы его собственной таблицей |
| объект «роль к биому», «имя варианта к варианту» | объект, где ключи — первое, а значения — второе: `{ "ocean": "mypack:ruby_ocean" }` |

Почти все описания принимают ещё и `requires` — список id модов или пространств имён паков, которые должны присутствовать, иначе файл пропускается.

## Единственное правило

Откройте jar мода, найдите файл, который хотите заменить, и скопируйте его путь начиная с `assets`.

Текстура железной руды внутри jar Minecraft лежит здесь:

```
assets/minecraft/textures/blocks/iron_ore.png
```

Значит, ваша версия кладётся сюда:

```
rdploader/assets/minecraft/textures/blocks/iron_ore.png
```

Вот и вся система. Путь после `assets` всегда точно такой же, как внутри jar, так что переименовывать или переносить ничего не придётся или переносить.

## Как раскладывать паки

Отдельные файлы работают нормально, но их можно и сгруппировать — папкой или zip-архивом:

```
rdploader/MyTextures/assets/...
rdploader/MyTextures.zip
```

С папками удобнее, пока вы работаете. Zip удобнее отдавать другим. Ведут они себя одинаково.

**Какой пак победит.** Если в двух паках лежит один и тот же файл, поставьте в начало имени `RDPL` и число. Больший номер загружается позже и побеждает:

```
rdploader/RDPL0 BaseTextures.zip
rdploader/RDPL1 SeasonalTextures.zip
rdploader/RDPL9 ModFixes.zip
```

Регистр букв любой, пробел, дефис или подчёркивание после числа необязательны, а сам префикс в отображаемом имени пака не показывается. Пак без префикса загружается первым, то есть проигрывает любому пронумерованному.

Приоритет задаёт ещё и порядок генерации записей мира. Это важно, когда один пак кладёт блоки, заменяемые другим.

**Выключить пак, не удаляя его**, можно добавив `.disabled` в конец имени.

## Ресурспаки: кто главнее

По умолчанию ваши файлы стоят *выше* выбранных игроком ресурспаков, так что перебить их ресурспак не сможет. Для логотипа сборки это правильно. Для текстур, которые вы хотели бы дать людям перерисовать, — нет.

Добавьте `O` или `N` после префикса `RDPL`, чтобы решать это для каждого пака:

```
rdploader/RDPLO Branding        всегда побеждает, ресурспаки его не тронут
rdploader/RDPLN BaseTextures    ресурспак может его перебить
rdploader/RDPL1O Seasonal       приоритет и переопределение сразу
```

Паки без буквы следуют настройке `overrideResourcePacks` в конфиге. Команда `/rdpl list` помечает те, что переопределяют.

Буква должна заканчивать префикс, поэтому после неё нужен пробел, дефис или подчёркивание — либо ничего. Именно это не даёт паку с именем `RDPLOverhaul` потерять свою `O` и превратиться в `Overhaul`.

## Паки только на сервере

Пак может жить на одном сервере, а все игроки — сидеть на чистом ванильном клиенте. Условие одно: **ничто в нём не должно ничего регистрировать**. Сам мод присутствия на клиенте не требует: оба его id принимают любую удалённую версию. Решает именно пак. Ванильный клиент играет с теми списками блоков, предметов и звуков, с которыми вышел. Пак, добавляющий в эти списки, обязан стоять с обеих сторон — а это уже раздача сборки, и весь этот раздел перестаёт действовать.

Что остаётся на безопасной стороне, а что нет:

| Достаточно одного сервера | Пак нужен и на клиенте |
| --- | --- |
| `worldgen`, `worldtemplates`, `gamerules`, `structures` | `blocks`, `items`, `fluids`, `materials` |
| `recipes`, `recipe_removals`, `furnace`, `fuels`, `brewing`, `oredict` | `potions`, `potion_types`, `sounds`, `tabs` |
| `loot_tables`, `loot_injections`, `advancements`, `functions` | `biomes`, `dimensions` |
| `gates`, `trades`, `registry_remap` | `villagers` |
| весь слой управления, настройки и предгенерация | `models`, `blockstates`, `textures`, `lang` (клиентские папки: клиента нет, значит и их не надо) |

Папки реестров в правой колонке — это жёсткий запрет, а не пожелание: ванильный клиент, отправленный в измерение, о котором он никогда не слышал, отваливается на месте, а блоки, которых он не знает, ему даже нельзя описать. Левая колонка работает по двум причинам. Часть происходит целиком на сервере: генерация, лут, функции, удаления, слой управления. Остальное доходит до клиента пакетами, на которых ваниль и так говорит. Слот результата крафта в этой версии заполняет сервер. Достижения приходят обычными пакетами достижений, отказы ворот — простыми сообщениями статуса. Удержание при предгенерации собрано из ванильных пакетов игрового режима, заголовка и телепорта. Ванильного клиента удерживают, предупреждают и встречают ровно так же, как модифицированный.

Что делать, по порядку:

1. Включите `vanillaClients` в конфиге, в категории `content`. Это правая колонка как правило, а не как дисциплина. Всё оттуда пропускается при загрузке, пропущенные файлы каждого пака называются в логе, и ничто не регистрируется. Случайно попавший файл блока станет строчкой в логе, а не отказом в подключении. Нужен перезапуск, как и всему, что решает, что регистрируется.
2. Всё равно держите описания подальше от папок правой колонки. Переключатель охраняет дверь, но бездействующие файлы — мёртвый груз. Везде, где пак тянется к предмету — `hold` у ворот, `killedDrops`, результат рецепта, обмен, — называйте только ванильные предметы или предметы других двусторонних модов сервера.
3. Варианты сущностей можно оставить, но с открытыми глазами. Характеристики, дроп и спавн применяет сервер, а внешность рисует клиент. Ванильный клиент увидит обычное существо с новым поведением. Если весь смысл во внешности, пак уже не серверный.
4. Положите пак на сервер как обычно, в серверную папку паков. На чужие машины ничего не ставится, а `/rdpl` у них не появится: команда принадлежит моду, а не игре.
5. Проверьте раньше, чем это сделают игроки: зайдите один раз чистым ванильным клиентом той же версии. Ошибка здесь громкая, а не тихая: соединение отклоняется или рвётся прямо на входе. Один чистый вход и есть настоящая проверка.
6. Заранее примите два косметических пробела. Добавленные сервером рецепты крафтятся нормально, но в книге рецептов не появляются. Варианты сущностей, меняющие только поведение, выглядят стандартно. Всё остальное — сгенерированный мир, правила, лут, закрытые измерения, предгенерация с удержанием и приветствием — тот же самый опыт, что и у модифицированного клиента.

# Переопределение

## Что можно переопределить

- **Что угодно из папки assets мода** — текстуры, модели, blockstates, языковые файлы, звуки, шрифты, надписи на заставке, справочники, руководства
- **Достижения и таблицы лута**, на стороне сервера, так что работают и на выделенных серверах
- **Рецепты** — заменить рецепт мода или добавить свой
- **Шаблоны структур** — файлы `.nbt` для генерируемых модами построек, в папке `structures/`
- **Функции**, файлы `.mcfunction` в папке `functions/`
- **Переименования в реестрах** — чтобы старые миры продолжали работать после того, как мод переименовал блок или предмет
- **Удаление рецептов** — убрать рецепт крафта по имени, пространству имён или результату
- **Добавки в лут** — добавить пул в таблицу лута вместо замены её целиком
- **Имена словаря руд, рецепты печи, время горения топлива, творческие вкладки и звуковые события**

RDPL хорош, чтобы заменить один-два рецепта, а рецепты для собственного контента и должны лежать в паке рядом с ним. Для полного управления рецептами по всей сборке лучше подойдут CraftTweaker и GroovyScript. Файл здесь всё равно заменяет оригинал целиком. Надо поменять один ингредиент или убрать одну запись лута — берите их.

### Настройки пака

Рядом с `assets` пак может нести папку `config` с JSON-файлами, где перечислены переключатели true/false и их значения по умолчанию:

    PackA.zip/config/options.json
    { "enableTestingContent": true, "enableLoserBlocks": false }

Файл с `"hide": true` на верхнем уровне убирает настройки пака и из экрана настроек, и из создаваемого файла. Управлять контентом они при этом продолжают, со своими значениями по умолчанию. Нужно это в двух случаях. Первый — контент ещё не готов к выпуску. Второй — паки-шаблоны, где настройки связывают описания между собой, а выбором ни для кого не являются. Уберите ключ, чтобы их опубликовать. То же работает и для отдельной настройки. `"hide": true` внутри объекта настройки прячет только её. Готовый пак может нести переключатель для незаконченного контента или затвор для шаблона, и ни то, ни другое не будет видно:

    { "enablePackB": { "default": false, "hide": true } }

Спрятанную настройку переключить нельзя. Значит, спрятанная со значением true включена навсегда. Это для контента, встроенного в механику настроек, но не являющегося выбором.

Настройка может быть и объектом с описанием — оно показывается под её именем в экране настроек:

    { "enableTestingContent": { "default": true, "description": "Registers the test blocks and items" } }

При запуске файлы настроек пака превращаются в один настоящий конфиг, названный по паку: `rdploader/config/PackA.json`. Он принадлежит пользователю. Создаётся со значениями пака по умолчанию, а при обновлении дополняется: новые настройки появляются, не трогая уже заданное. Изменения применяются при следующем запуске игры. Настройки бывают только у именованных паков: папки или zip. Создаваемый файл называется по паку, а отдельные файлы в `rdploader/assets` имени не имеют и настроек не несут. Нужен переключатель — заверните такой контент в именованную папку.

После этого список `requires` любого описания может назвать настройку записью `config:`. Например, `"requires": ["config:enableTestingContent"]` регистрирует контент, только пока настройка включена. Работает это как отсутствующий мод: выключено — пропущено. Голое имя проверяется по файлам всех паков, и каждый задающий её пак должен согласиться; `"config:PackA:enableTestingContent"` называет один пак. Настройка, не заданная ни одним паком, считается выключенной, и об этом один раз предупреждают.

Запись `file:` проверяет, есть ли файл или папка внутри папки игры. Так контент связывают с чем-то за пределами собственных паков RDPL — например, с ресурспаком другого мода: `"requires": ["file:config/StarMaker/resources/0_jackspace2_celestialpack.zip"]` регистрирует контент, только пока этот файл установлен. Путь задаётся относительно папки игры, всегда через прямые слэши. Символы `..` в нём запрещены.

### Наследование описаний

Описание блока или предмета может отталкиваться от другого того же вида через `"inherits"`, называя registry name любого варианта, а затем переопределять то, что отличается:

    { "inherits": "mypack:ruby_ore",
      "variants": { "sapphire_ore": { "meta": 0, "hardness": 4.0 } } }

Потомок копирует все характеристики файла-родителя и названного варианта. Порядок файлов не важен, цепочки разрешаются от родителя вниз. Кольцо или пропавший родитель попадают в лог, а потомок остаётся как написан. Поля, написанные потомком, заменяют унаследованное значение. Вложенные свойства варианта переопределяются по одному. Списки вроде `requires` заменяются целиком — пишите весь нужный список. Блоки наследуются только от блоков, предметы — только от предметов.

### Шаблоны блоков и предметов

Родитель может быть чистым шаблоном и в игру не попадать вовсе: наследование читает сами файлы описаний, а не то, что зарегистрировалось. Закройте шаблон спрятанной настройкой, принудительно выключенной, и он ничего не зарегистрирует, а его характеристики останутся доступными для наследования:

`config/options.json`

```json
{
  "templates": { "default": false, "hide": true, "description": "Never on, parents only" }
}
```

`assets/jacksmod/blocks/ore_template.json`

```json
{
  "type": "ore",
  "material": "rock",
  "soundType": "stone",
  "harvestTool": "pickaxe",
  "harvestToolLevel": 2,
  "creativeTab": "jacksmod:tab",
  "expDrop": { "min": 2, "max": 5 },
  "requires": ["config:templates"],
  "variants": {
    "ore_template": { "meta": 0, "hardness": 3.0, "resistance": 5.0 }
  }
}
```

`assets/jacksmod/blocks/jacks_ore.json`

```json
{
  "inherits": "jacksmod:ore_template",
  "requires": [],
  "variants": {
    "jacks_ore": { "meta": 0, "hardness": 4.0 }
  }
}
```

Шаблон не регистрируется никогда. `jacks_ore` берёт от него материал, звук, инструмент, вкладку, выпадающий опыт и сопротивление, переопределяя только твёрдость. Потомок обязан написать собственный `requires` — здесь пустой список. Иначе он унаследует родительский и исчезнет вместе с родителем.

### Структуры в точных местах

Ванильные структуры прикрепляются к точным местам через `structureAt` в настройках `terrain`, записями вида `structure=x,z`, по одной на строку: `"structureAt": ["villages=1000,-500"]`. **x и z здесь — координаты блоков, а не чанков**, и структура генерируется в том чанке, где лежит этот блок. По одной записи на каждый нужный экземпляр. Шаг сетки, разделение, минимальное расстояние от точки появления и проверки ровной земли отходят в сторону, так что за место отвечает пак: два пина ближе чанка друг к другу поставят две структуры в один чанк. Сама структура садится на землю в своём чанке по обычным правилам, как только заложена.

Запись `imprint` прикрепляется так же — через `"at": [x, z]` в её `shape`. Она ставится ровно один раз в этих координатах на поверхности, когда генерируется тот чанк, а не по случайности. Это сочетается с `locateAs`, поэтому прикреплённую структуру можно ещё и находить через /locate.

### Как находить поставленные структуры

Запись `imprint` с `"locateAs": "Crypt"` регистрирует под этим именем каждую поставленную ею структуру. `/locate Crypt` затем указывает на ближайшую, а само имя предлагается в автодополнении. Найти можно только уже сгенерированные структуры. Структуры пака ставятся по случайности при создании чанков, а не по предсказуемой для игры сетке. Имена живут в сохранении мира, так что переживают перезапуск и работают на серверах.

## Переименования в реестрах

Когда мод переименовывает свой блок или предмет, миры, сохранённые до переименования, их теряют. Положите файл в `registry_remap/`, чтобы сопоставить старое имя новому:

```json
{
  "registry": "minecraft:items",
  "mapping": { "oldmod:old_name": "newmod:new_name" }
}
```

Реестр — тот, где лежит запись, обычно `minecraft:items` или `minecraft:blocks`. Переименования выстраиваются в цепочку: сопоставили A с B, потом B с C — и A уходит сразу в C.

# Справочник

## Списки значений

Это имена, принимаемые разборщиком везде, где в таблицах выше написано «один из материалов» и тому подобное. Всё неопознанное попадает в лог и заменяется значением по умолчанию.

**Материалы блоков.** `air`, `grass`, `ground`, `wood`, `rock`, `iron`, `anvil`, `water`, `lava`, `leaves`, `plants`, `vine`, `sponge`, `cloth`, `fire`, `sand`, `circuits`, `carpet`, `glass`, `redstone_light`, `tnt`, `coral`, `ice`, `packed_ice`, `snow`, `crafted_snow`, `cactus`, `clay`, `gourd`, `dragon_egg`, `portal`, `cake`, `web`, `piston`, `barrier`, `structure_void`.

**Типы звука.** `wood`, `ground`, `plant`, `stone`, `metal`, `glass`, `cloth`, `sand`, `snow`, `ladder`, `anvil`, `slime`.

**Цвета на карте.** `air`, `grass`, `sand`, `cloth`, `tnt`, `ice`, `iron`, `foliage`, `snow`, `clay`, `dirt`, `stone`, `water`, `wood`, `quartz`, `adobe`, `magenta`, `light_blue`, `yellow`, `lime`, `pink`, `gray`, `silver`, `cyan`, `purple`, `blue`, `brown`, `green`, `red`, `black`, `gold`, `diamond`, `lapis`, `emerald`, `obsidian`, `netherrack`.

**Слои отрисовки.** `solid`, `cutout`, `cutout_mipped`, `translucent`. Если не задано, блок выбирает подходящий своему типу.

**Редкость.** `common`, `uncommon`, `rare`, `epic`.

**Частицы факела.** `none`, `flame`, `colored`. Для `colored` используется `particleColor`.

**Классы инструментов.** `pickaxe`, `axe`, `shovel`, `sword`.

**Слоты брони.** `head` или `helmet`, `chest` или `chestplate`, `legs` или `leggings`, `feet` или `boots`.

**Оттенки.** `biome`, `none` либо шестизначный hex-цвет. Цвета в любом описании задаются в hex, с ведущей `#` или без.

**Поведение** для `behavesAs`. `till`, `path`.

**Имя нового мира** задаётся через `worldName` в группе `terrain`. Экран создания мира открывается с этим именем уже в поле, а папка, куда мир сохраняется, следует из него как обычно. Поле заполняется, только пока в нём стоит написанное самой игрой, так что имя, набранное игроком, не отбирают. В отличие от сида и игрового режима обратно оно не возвращается: как мир назван при создании, так и называется.

**Игровой режим** задаётся через `worldGameMode` в группе `terrain`, одно из `survival`, `creative`, `adventure` или `spectator`. Каждый мир, созданный при включённом паке, начинается так, а `creative` заодно открывает команды — то же самое, что поставить галочку вручную при создании мира. Он решает только, как мир начинается; смену режима внутри мира потом никто не трогает. Экран создания мира открывается с режимом и сидом, которые просит пак. Показанное там и есть то, что произойдёт. Игрок волен всё поменять перед созданием, даже если пак вернёт своё. `adventure` и `spectator` на этом экране не предлагаются. Пак, просящий любой из них, оставляет показанным выбранное, а режим ставит уже при создании мира.

**Где появляется новый мир** задаётся через `worldSpawn` в группе `terrain`, записью `x,z` или `x,y,z`. Без y берётся обычный для этого типа мира уровень земли — то самое, что ваниль и так сохраняет, — и игрока ставят на поверхность там. Применяется при создании мира: уже существующий сохраняет ту точку появления, с которой родился. Запись не из целых чисел отмечается в логе и оставляется игре.

Особенно это стоит знать про плоские миры. Игра выбирает точку появления, ища траву на уровне моря. На суперплоском мире блок над стопкой слоёв всегда воздух, проверка не проходит никогда, и игра уходит искать на тысячу шагов. Плоский мир поэтому может открыться в сотнях блоков от начала координат, совсем не там, где пак ожидает. Указанный `worldSpawn` это решает.

**Граница мира** задаётся через `worldBorder` в группе `terrain`, целым числом блоков в поперечнике — та же величина, что и у `/worldborder set`. Применяется при создании мира, поэтому существующий мир сохраняет свою границу, а `0`, значение по умолчанию, оставляет границу там, где её ставит игра. Центр там, где его ставит игра, и границу по-прежнему можно двигать командой обычным способом.

Пак не может задать границу любого размера. `worldBorderLimit` в конфиге — самое широкое, что паку разрешено просить. Просящему больше отказывают прямо, а не урезают молча: причина уходит в лог, граница остаётся нетронутой. Поднять этот предел может только тот, кто запускает игру, так что пак не навяжет серверу границу, на которую тот не согласился.

**Время суток** фиксируется через `worldTime` в группе `terrain`, в тиках — та же величина, что и у `/time set`. `18000` это полночь, `6000` полдень. Часы обычного мира останавливаются на этом значении и больше не идут. Зафиксированное время получает всё, что спрашивает, день сейчас или нет, — включая спавн мобов и сон. `-1`, значение по умолчанию, оставляет время идти. Это версия `fixedTime` для обычного мира — того самого, который может задать ваше собственное измерение. В отличие от `doDaylightCycle` здесь неважно, что показывали часы при создании мира.

**Структуры** для шаблона мира. `villages`, `mineshafts`, `strongholds`, `temples`, `monuments`, `mansions`, `netherbridges`, `endcities`, `caves`, `ravines`.

**Типы существ** для спавна и частоты в биомах. `creature`, `monster`, `ambient`, `water_creature`.

## Команды

`/rdpl` выполняется на вашей машине и не требует прав, потому что только читает файлы, которые у вас и так есть. Работает на любом сервере, независимо от того, стоит ли мод на сервере.

| Команда | Что делает |
| --- | --- |
| `/rdpl list` | Все загруженные паки, их приоритет и содержимое. Щелчок по паку ищет в нём файл |
| `/rdpl which <namespace:path>` | Какой пак даёт этот файл и какие паки он перекрывает |
| `/rdpl reload` | Пересканировать папку и перезагрузить всё |
| `/rdpl reload <group>` | Перезагрузить только один вид: `textures`, `models`, `languages`, `sounds` или `shaders` |
| `/rdpl unused` | Файлы в ваших паках, которые пока никто не запрашивал, обычно опечатка в пути |
| `/rdpl biome list` | Все биомы, способные генерироваться, и их id |
| `/rdpl biome here` | Биом, в котором вы стоите |
| `/rdpl biome find <name>` | Ближайшее место, где генерируется биом, без генерации чанков для поиска |

На выделенном сервере `/rdplserver` делает то же самое для серверной копии папки и требует прав оператора.

| Команда | Что делает |
| --- | --- |
| `/rdplserver reload` | Пересканировать серверную папку и перезагрузить всё |
| `/rdplserver list` | Все паки, загруженные сервером, их приоритет и содержимое |
| `/rdplserver which <namespace:path>` | Какой пак даёт этот файл и какие паки он перекрывает |
| `/rdplserver unused` | Файлы в паках сервера, которые никто не запрашивал |
| `/rdplserver oregen` | Текущие счётчики заблокированной генерации руды, по модам и типам |
| `/rdplserver biome` | Все биомы, способные генерироваться на сервере |
| `/rdplserver dimensions` | Все измерения, включая добавленные паками |
| `/rdplserver gate list` | Все ворота и открыты ли они |
| `/rdplserver gate check <player>` | Какие ворота игрок прошёл |
| `/rdplserver gate grant <player> <gate>` | Открыть ворота игроку |
| `/rdplserver gate revoke <player> <gate>` | Закрыть обратно |
| `/rdplserver intro` | Дать вступлению к миру сыграть снова при следующем входе |
| `/rdplserver goto <структура>` | Отправляет к ближайшей, где ещё никто не был, и ищет, не создавая землю по дороге |
| `/rdplserver goto <структура> next` | Отправляет дальше, к ближайшей из тех, куда вас за эту сессию ещё не отправляли, — посещали её раньше или нет |
| `/rdplserver goto <структура> back` | Возвращает к предыдущей, шаг за шагом по тем местам, куда вас отправила эта сессия |

**Повседневная работа:** `/rdpl reload textures` заметно быстрее, чем F3+T в большой сборке. F3+T по-прежнему работает и перезагружает всё. Обычный `/rdpl reload` нужен, когда вы *добавляете* или *удаляете* файл, потому что это меняет состав папки.

## Полезно знать

- CraftTweaker и GroovyScript выполняются после RDPL, поэтому их изменения всё равно побеждают.
- Рецепты загружаются только при запуске, поэтому изменения рецептов требуют перезапуска, а не перезагрузки.
- Функции, сохранённые в собственной папке данных мира, всё равно побеждают функцию из пака, и то же касается собственных достижений этого мира.
- Уже сгенерированная структура остаётся загруженной, пока вы не выйдете из мира.
- Регистр в имени файла важен. Если написание вашего файла не совпадает с запрошенным, RDPL всё равно его загрузит, но предупредит: на Linux он бы вообще не нашёлся.
- Положите `pack.png` в `rdploader`, чтобы дать паку значок.
- Папку можно перенести или переименовать настройкой `rootDirectory` в `config/mct_resourcedatapackloader_mixin.cfg`. Абсолютный путь тоже работает, и нужен перезапуск.
- Blockstates, называющие голую ванильную модель, наследуют и ванильные текстуры. Родительские модели вроде `cube_all` и `cross` берут текстуры из blockstate, и с ними всё в порядке.
- `forge_marker: 1` не поддерживает multipart, поэтому blockstates для лозы должны быть обычным ванильным multipart с текстурами, запечёнными в модель.

## Когда что-то не работает

**Сначала смотрите `logs/rdpl.log`.** Всё, что делает RDPL, пишется туда, а не в основной лог. Достижения, таблицы лута, рецепты, функции, структуры и каждая единица контента записываются вместе с паком, из которого пришли, а всё некорректное — с причиной.

**С текстурами и прочими ресурсами иначе.** Их запрашивают слишком часто, чтобы писать каждый в лог. Вместо этого `/rdpl unused` перечисляет файлы ваших паков, которые никто не запрашивал. Запускайте её, когда игра догрузилась. Файл с правильным путём запрашивается всегда, так что перечисленное обычно означает опечатку. Помните только, что часть файлов грузится по необходимости — например, языки, отличные от вашего.

**Папка или zip пака без каталога `assets` внутри пропускается,** и лог об этом говорит.

**`/rdpl which minecraft:textures/blocks/stone.png`** точно скажет, какой пак отдаёт файл и что он перекрывает.

## Бонус: ванильные твики

Небольшие изменения ванильного поведения, каждое переключается в категории конфига `tweaks`.

| Настройка | По умолчанию | Что делает |
| --- | --- | --- |
| `promptLeafDecay` | вкл | Листва, потерявшая своё дерево, опадает за секунду, а не ждёт случайных тиков |
| `lenientPaths` | вкл | Тропинку можно сделать под блоком, и она остаётся, когда сверху ставят блок |
| `unbreakableSpawners` | выкл | Спавнеры нельзя сломать или взорвать |

Ещё три лежат в категории `content`, а не `tweaks`:

| Настройка | По умолчанию | Что делает |
| --- | --- | --- |
| `cactusMaxHeight` | `3` | Насколько высоким вырастает ванильный кактус |
| `caneMaxHeight` | `3` | Насколько высоким вырастает ванильный тростник |
| `shovelPaths` | вкл | Лопата превращает блоки с пометкой `behavesAs` path в тропинку, а приседание возвращает обратно |

**Они уступают Universal Tweaks**, который меняет те же ванильные блоки. Когда именно — смотрите [Universal Tweaks](#universal-tweaks).

**Ничего из этого не касается пака.** Эти настройки меняют только собственные кактус, тростник, листву и тропинки Minecraft. Блок, описанный вашим паком с `"type": "cane"`, несёт собственную секцию `growth` и вырастает до той высоты, какую вы задали, что бы ещё ни стояло. `lenientPaths` заодно снимает то же ограничение с блоков пака, использующих `behavesAs`, чего Universal Tweaks не трогает, так что эта половина остаётся включённой в любом случае.

### Неразрушимые спавнеры

`unbreakableSpawners` даёт блоку спавнера показатели бедрока: неразрушимую твёрдость и сопротивление взрыву, которое ничто не переживает. Игрок не сломает его никакой киркой, и ни криперы, ни динамит, ни сущность пака со свойством `explodes` его не уберут. Творческий режим по-прежнему их удаляет, ровно так же, как по-прежнему удаляет бедрок, поэтому автор пака никогда не окажется заперт снаружи собственной постройки. Требуется перезапуск, потому что значения выставляются один раз при завершении загрузки игры.

**Это блок, а не спавнер.** Переключателя для отдельного спавнера нет. Настройка меняет сам `minecraft:mob_spawner` и действует сразу на все спавнеры в мире: на четыре ванильные структуры, на поставленные модом и на поставленные вашими паками.

Последнее и есть ответ для собственной структуры. Спавнер внутри вашего шаблона `.nbt`, поставленный записью `imprint`, — обычный блок спавнера со своим tile entity. Он покрыт с момента включения настройки. Стройте структуру со спавнером обычным способом. Задайте, кого он спавнит, в данных tile entity шаблона. Включите `unbreakableSpawners` — и тот, что в вашем подземелье, станет так же неразрушим, как ванильный. В пак для этого ничего не кладётся, и защитить только свои, оставив остальные в мире ломаемыми, никак нельзя.

## Бонус: исправление конфликта плагинов JEI

Некоторые моды опрашивают реестр рецептов JEI раньше, чем его успевают наполнить. Логи заливает сотнями безобидных, но шумных ошибок, а интеграция мода с JEI может незаметно сломаться. RDPL определяет это автоматически и исправляет порядок оповещения. Работает и с Just Enough Items, и с Had Enough Items. Если не установлено ни то, ни другое, ничего не происходит.

## Бонус: меньше ошибок при запуске

- Рецепты, ссылающиеся на предмет, который ни один мод не зарегистрировал (обычно контент, выключенный в конфиге самого мода), пропускаются, а не бросают ошибку разбора. Количество один раз пишется в лог. (`skipMissingItems`)
- Достижения, награждающие рецептом, который скрипт с тех пор удалил, всё равно загружаются, а не падают. Просто этот рецепт они никогда не откроют, а весь набор сводится в одну строку лога. (`tolerateMissingInAdvancements`)

## Группы твёрдости

`hardness/*.json` задаёт группе блоков множитель времени добычи, который разыгрывается для каждой позиции блока. Сам блок при этом не меняется: ничего не регистрируется, ничего не пишется в мир, и мир, открытый без пака, остаётся обычным ванильным.

```json
{
  "blocks": ["minecraft:stone:0"],
  "miningTime": { "min": 1.0, "max": 20.0 },
  "buckets": 10,
  "field": { "type": "speckle", "spread": 0.15 }
}
```

| Ключ | Обязателен | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `blocks` | да | список имён блоков или объектов |, | Сама группа. Те же три формы, что у `replace` в генерации |
| `except` | нет | список имён блоков или объектов | нет | Изымается из группы, что бы ни говорил `blocks` |
| `miningTime` | нет | число или объект с `min` и `max` | `1.0` | Во сколько раз дольше ломается блок |
| `blastResistance` | нет | число или объект с `min` и `max` | `1.0` | Умножает взрывоустойчивость блока |
| `buckets` | нет | от 1 до 256 | `10` | На сколько ступеней делится диапазон |
| `minHeight` | нет | целое | `0` | Ниже этого выпадает самая твёрдая ступень |
| `maxHeight` | нет | целое | `255` | Выше этого выпадает самая твёрдая ступень |
| `field` | нет | объект | см. ниже | Форма, в которую собирается результат |
| `requires` | нет | список id модов или пространств имён паков | нет | Файл пропускается, если есть не всё |

Одно число даёт всем блокам группы один и тот же множитель, и ничего не разыгрывается. `min` и `max` разыгрываются по позиции: `max` там, где поле пусто, `min` в середине сгустка, а ступени между ними задаёт `buckets`.

### Поле

Розыгрыш идёт не для каждого блока сам по себе, иначе твёрдое и мягкое были бы чистым шумом без всякой формы. `field` задаёт, какая форма получится, а `type` выбирает между двумя способами.

| Ключ | Обязателен | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `type` | нет | `speckle` или `seeded` | `speckle` | Какой из двух вариантов ниже используется |

#### speckle

Каждый блок тянет свою ступень, а блок через грань может передать ему ступень послабее. Получается частая мелкая крапина, чаще всего в один блок, изредка с более крупным сгустком там, где они сходятся. Из двух вариантов этот ближе к тому, как ощущается добыча в исходном моде.

| Ключ | Обязателен | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `chances` | нет | список целых, на тысячу | `[30, 30, 20, 20, 10, 10, 10, 10, 50]` | Как часто блок начинает с той или иной ступени, самая мягкая последней. Остаток приходится на самую твёрдую |
| `spread` | нет | от 0.0 до 1.0 | `0.15` | Как часто ступень переходит на соседний блок, ослабев на одну–три |

Список читается так, что последняя запись — самая мягкая ступень, а первая на одну выше самой твёрдой. С числами выше примерно семь блоков из десяти — самая твёрдая ступень, остальные рассыпаны между ними.

#### seeded

Зёрна стоят на решётке, выведенной из мира и позиции, а ступень блока зависит от того, насколько он близок к ближайшему зерну. Получаются более редкие, крупные и округлые сгустки, перетекающие друг в друга, и они умеют пускать лучи.

| Ключ | Обязателен | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `cell` | нет | целое, блоки | `8` | Как далеко друг от друга стоят зёрна |
| `seeds` | нет | от 1 до 4 | `1` | Зёрен в одной ячейке |
| `reach` | нет | дробное, блоки | `3.0` | Насколько далеко действует зерно |
| `arms` | нет | от 0 до 6 | `0` | Лучи, расходящиеся от каждого зерна |
| `armReach` | нет | дробное, блоки | `0.0` | Насколько далеко тянутся лучи |

Без `arms` сгустки круглые. Если дать зерну лучи, оно становится узлом с усиками, и лучи соседних узлов тянутся друг к другу — это уже жила, а не комок. Держите `reach` больше половины `cell`, иначе сгустки не смогут соприкоснуться и останутся отдельными шарами без всего между ними.

### Как показать это игроку

Сам по себе множитель невидим. Чтобы игрок видел, какие блоки крепкие, дайте блоку blockstate с одной вариантой на ступень, все с одинаковым весом, от самой твёрдой:

```json
{
  "variants": {
    "normal": [
      { "model": "mypack:stone_step0", "weight": 1 },
      { "model": "mypack:stone_step1", "weight": 1 }
    ]
  }
}
```

Minecraft и так выбирает варианту по позиции блока, а группа твёрдости передаёт ему вместо этого номер ступени, так что текстура и множитель всегда сходятся.

Три вещи должны быть верны, и ни одна из них не сообщит о себе, если она неверна.

**Ровно `buckets` записей, все одного веса.** Ступень используется как место в списке, поэтому список другой длины или с разными весами молча указывает на не ту текстуру.

**Имя модели без `block/` впереди.** Blockstate сам добавляет `block/`, поэтому `"model": "mypack:step_stone"` читает файл `models/block/step_stone.json`. Если написать `mypack:block/step_stone`, поиск пойдёт в `models/block/block/step_stone.json`, которого нет, и запись отбрасывается без единого слова.

**Тот же ключ, о котором спрашивает игра.** Не всякий блок записан так, как читаются его свойства. Ванильный камень хранит всё под `normal`, а не под `variant=stone`, поэтому замена, где написан только `variant=stone`, объединяется и затем ни разу не используется. Писать оба ключа безопасно: объединение идёт по ключам, и пак перебивает то, что было до него.

Включите `worldgenDebug`, и при входе в мир каждая группа твёрдости сверяется со своей запечённой моделью: какой blockstate, сколько вариант уцелело, какая текстура досталась каждой и какие паки игра для этого объединила. Это самый быстрый способ найти любой из трёх пунктов выше, а также предупреждение, если замена общего blockstate изменила состояние, которого группа не называла.

### Чего это не затрагивает

Меняется только добыча самим игроком. Машины, ломающие блоки, читают твёрдость напрямую и ничего не замечают. Блоки, поставленные игроком, разыгрываются наравне со всеми, потому что розыгрыш принадлежит месту, а не блоку, и перенесённый блок принимает то, что говорит его новое место.

# Генерация

## Записи генерации мира

`worldgen/*.json` описывает то, что генерируется. Каждая запись — это **форма**, размещённая **распределением** и отфильтрованная по тому, где ей позволено быть.

```json
{
  "block": "mypack:ruby_ore",
  "meta": 0,
  "size": 8,
  "attempts": 12,
  "replace": ["minecraft:stone"],
  "dimensions": [0],
  "dimensionsAreBlacklist": false,
  "biomes": ["minecraft:extreme_hills"],
  "biomeTypes": ["MOUNTAIN"],
  "biomesAreBlacklist": false,
  "minTemperature": -100.0,
  "maxTemperature": 100.0,
  "minRainfall": -100.0,
  "maxRainfall": 100.0,
  "minHeight": 8,
  "maxHeight": 48,
  "minDistanceFromSpawn": 0,
  "sparse": false,
  "retrogen": false,
  "retrogenKey": "ruby_v1",
  "requires": ["quark"],
  "shape": { "type": "cluster" },
  "spread": { "type": "even" }
}
```

Обязателен только `block`; всё остальное можно не писать, и оно возьмёт значение по умолчанию. `blocks` заменяет `block`, когда одного мало, и у него свой пример ниже.

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `block` | да | имя блока |, | Что ставится |
| `meta` | нет | int | `0` | Какой вариант этого блока |
| `blocks` | нет | список объектов | нет | Взвешенный список вместо одного блока. См. ниже |
| `size` | нет | int или диапазон | `8` | Сколько блоков ставит одна попытка, либо насколько велика форма с радиусом |
| `attempts` | нет | int или диапазон | `1` | Сколько попыток на чанк |
| `replace` | нет | список имён блоков или объектов | `["minecraft:stone"]` | Что можно заменять. См. ниже |
| `adjacent` | нет | список имён блоков или объектов | нет | Ставит только там, где один из них есть среди 26 блоков, касающихся места. Те же три формы, что у `replace` |
| `minHeight` | нет | int | `0` | Самый низкий y для установки |
| `maxHeight` | нет | int | `64` | Самый высокий y для установки |
| `dimensions` | нет | список целых | все измерения | В каких измерениях работает |
| `dimensionsAreBlacklist` | нет | boolean | `false` | Превратить этот список в список исключений |
| `biomes` | нет | список имён биомов | все биомы | В каких биомах работает |
| `biomeTypes` | нет | список типов словаря | нет | Биомы по типу, например `FOREST` или `NETHER` |
| `biomesAreBlacklist` | нет | boolean | `false` | Превратить эти списки в списки исключений |
| `minTemperature` | нет | float | `-100.0` | Самый холодный биом, где генерируется |
| `maxTemperature` | нет | float | `100.0` | Самый тёплый биом, где генерируется |
| `minRainfall` | нет | float | `-100.0` | Самый сухой биом, где генерируется |
| `maxRainfall` | нет | float | `100.0` | Самый влажный биом, где генерируется |
| `minDistanceFromSpawn` | нет | int, блоки | `0` | Насколько далеко от точки появления мира начинается |
| `sparse` | нет | boolean | `false` | Разбрасывает блоки, вместо того чтобы плотно их собирать |
| `retrogen` | нет | boolean | `false` | Генерировать и в уже существующие чанки |
| `retrogenKey` | нет | строка | ключ из конфига | Переопределяет ключ retrogen только для этой записи |
| `requires` | нет | список id модов или пространств имён паков | нет | Запись пропускается, если присутствует не всё |
| `shape` | нет | объект | `{ "type": "cluster" }` | Какую форму принимает. См. [Формы](#формы) |
| `spread` | нет | объект | `{ "type": "even" }` | Где размещается. См. [Распределение](#распределение) |

### Взвешенные блоки

`blocks` заменяет `block`, когда одной записи мало. Веса относительные, так что 80 и 20 — это четыре к одному.

```json
{
  "blocks": [
    { "block": "minecraft:wool", "weight": 80, "properties": { "color": "magenta" } },
    { "block": "minecraft:wool", "weight": 20, "properties": { "color": "lime" } }
  ]
}
```

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `block` | да | имя блока |, | Что ставится |
| `meta` | нет | int | `0` | Какой вариант |
| `weight` | нет | int | `1` | Насколько часто выбирается этот против остальных |
| `properties` | нет | объект «свойство к значению» | нет | Свойства состояния блока по имени, для состояний без собственных метаданных |

`block` и `meta` всё равно обязательны на верхнем уровне файла, даже когда используется `blocks`; первая запись — хорошее значение, чтобы туда поставить.

### Цели замены

`replace` — это список, и каждая запись принимает одну из трёх форм.

| Форма | Пример | Чему соответствует |
| --- | --- | --- |
| Имя | `"minecraft:stone"` | Любому состоянию этого блока |
| Имя и метаданные | `"minecraft:stone:3"` | Только этим метаданным, здесь диориту |
| Объект | `{ "block": "minecraft:stone", "properties": { "variant": "andesite" } }` | Только этому состоянию |

Форма-объект принимает и `meta` вместо `properties`, что то же самое, что запись через двоеточие. Используйте `"minecraft:air"`, чтобы генерировать в открытом пространстве.

### Соседние блоки

`adjacent` принимает те же три формы, что и `replace`, и добавляет к нему второе условие: место занимается, только если хотя бы один из 26 касающихся его блоков — по граням, рёбрам и углам — подходит под список. Без этой записи ничего не проверяется.

```json
{
  "block": "mypack:sulfur_ore",
  "replace": ["minecraft:sandstone"],
  "adjacent": ["minecraft:air"]
}
```

Так сера попадает в песчаник только там, где он и без того открыт в пещеру или наружу, а закопанный песчаник остаётся нетронутым. Соседи в чанках, которых ещё нет, считаются неподходящими, а не читаются, поэтому проверка никогда не вызывает генерацию чанка.

Это соблюдает любая форма, потому что решение принимается о каждом отдельном блоке. `geode` называет корку и заполнение отдельно, и эти два ставятся без проверки.

Запись, называющая только незарегистрированные блоки, пропускается с ошибкой, а не генерируется повсюду.

## Формы

Блок `shape` с ключом `type`. Ключи, не перечисленные для типа, им игнорируются.

| Тип | Что получается |
| --- | --- |
| `cluster` | Обычная жила, по умолчанию. Использует `size` |
| `largevein` | Длинная блуждающая жила с ответвлениями. Использует `size` |
| `plate` | Плоский диск |
| `geode` | Полая полость с коркой |
| `decoration` | Разброс по поверхности: цветы, грибы. Использует `size` |
| `tree` | Целое дерево |
| `vines` | Лозы на том, что уже стоит. Использует `size` |
| `basin` | Чаша, углубляющаяся к середине |
| `spire` | Сужающаяся колонна |
| `nodule` | Неровный шар |
| `vent` | Узкая колонна, останавливающаяся при столкновении |
| `imprint` | Один из ваших шаблонов `.nbt`. Тот, что помещается в чанк, сдвигается так, чтобы целиком лечь в строящийся чанк, а не заезжать в соседний, которого ещё нет, как бы он ни был повёрнут; тот, что больше чанка, ставится только там, где земля вокруг уже существует |
| `belt` | Скопление, охватывающее несколько чанков, для каменных областей |
| `field` | Жилы, вычисляемые сразу для каждого блока, с той же формой, что у групп твёрдости |

| Ключ | Для чего | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `type` | все | одна из форм выше | `cluster` | Какая форма |
| `radius` | plate, geode, basin, spire, nodule, vent | int или диапазон | `6` | Насколько широкая |
| `height` | plate, geode, basin, spire, vent, tree | int или диапазон | `1`, `8` для geode, `5` для tree | Насколько высокая или толстая |
| `width` | geode | int или диапазон | `12` | Общий размах полости |
| `plane` | plate, basin, spire, vent | `circle`, `square` | `circle` | Её след на плоскости |
| `slim` | plate, largevein, nodule | boolean | `false` | Plate: на слой тоньше. Largevein: ответвления в один блок. Nodule: полая оболочка |
| `hanging` | spire, vent | boolean | `false` | Расти вниз от потолка, а не вверх от пола |
| `taper` | spire | `straight`, `bell`, `needle` | `straight` | Как ширина спадает к вершине. `straight` сужается равномерно, `bell` держит ширину внизу и потом обрывается, `needle` сразу утончается в длинное остриё |
| `outline` | geode | имя блока | нет | Блок корки |
| `fill` | geode | имя блока | нет | Чем заполнена середина. Если не задано, середина полая |
| `surface` | decoration, tree | список имён блоков | нет | На чём может стоять |
| `seeSky` | decoration | boolean | `true` | Ставить только там, где видно небо |
| `checkStay` | decoration | boolean | `true` | Ставить только там, где блок удержится |
| `stackHeight` | decoration | int или диапазон | `1` | Сколько штук ставить друг на друга |
| `scatterX` | decoration, tree | int | `8` | Насколько далеко разбредается вбок |
| `scatterY` | decoration, tree | int | `4` | Насколько далеко разбредается по вертикали |
| `scatterZ` | decoration, tree | int | `8` | Насколько далеко разбредается вбок |
| `log` | tree | имя блока | нет | Блок ствола |
| `leaves` | tree | имя блока | нет | Блок листвы |
| `vines` | tree | boolean | `false` | Свесить лозы с листвы |
| `structure` | imprint | `namespace:name` | нет | Шаблон, который ставится |
| `integrity` | imprint | от 1 до 100 | `100` | Доля блоков шаблона, которые действительно появятся, в процентах |
| `structures` | imprint | список | нет | Несколько шаблонов на выбор, каждый раз ставится один. Каждая запись — `{ "structure": "namespace:name", "weight": 3 }` либо голое имя для равных шансов. Перекрывает `structure` |
| `turns` | imprint | список | любой | Как может быть повёрнут: `none`, `quarter`, `half`, `threequarter`. Записи могут нести `weight`. Если не задано, все четыре равновероятны |
| `mirrors` | imprint | список | нет | Ещё и отразить: `none`, `leftright`, `frontback`, с необязательным `weight` |
| `rarity` | belt | int | `400` | Одно скопление на столько чанков |
| `rarityIsPerChunk` | belt | boolean | `false` | Превратить `rarity` в число скоплений на каждый чанк |

```json
{
  "shape": { "type": "geode", "radius": 6, "height": 8, "outline": "minecraft:obsidian", "fill": "minecraft:glowstone" }
}
```

```json
{
  "shape": { "type": "tree", "log": "mypack:ruby_log", "leaves": "mypack:ruby_leaves", "height": { "min": 4, "max": 7 }, "surface": ["minecraft:grass"] }
}
```

`tree` без `log` или `leaves` не генерирует ничего и пишет об этом в лог.

### Пояса

`belt` — это шар, намного больший одного чанка, для каменных областей, а не рудных жил. `radius` — это размер шара. Каждый чанк сам вычисляет по сиду мира и имени записи, где начинаются ближние к нему шары. Пояс выходит целым в любом порядке генерации, и в соседний чанк ничего не пишется.

```json
{
  "shape": { "type": "belt", "radius": 32, "rarity": 400 }
}
```

Пояс игнорирует `attempts` и `spread`, потому что ставится на чанк, а не на попытку. `minHeight` и `maxHeight` — полоса, в которой лежат центры, а шар выходит за неё на `radius`. `replace` решает, что он съедает. `biomes` и пределы температуры и влажности проверяются в центре. Пояс поэтому появляется целиком или не появляется вовсе, а не обрезается на границе биома.

Стоимость растёт как куб `radius`, а низкая `rarity` её умножает, поэтому начинайте со значений по умолчанию и поднимайте радиус медленно.

## Распределение

Блок `spread` с ключом `type`.

| Тип | Куда ставит |
| --- | --- |
| `even` | Куда угодно между высотами, равномерно. По умолчанию |
| `centered` | Со смещением к одной высоте, редея с расстоянием |
| `sprawl` | Фрактальные жилы, охватывающие диапазон высот |
| `terrain` | Следуя поверхности |
| `cavern` | На полу пещер или на потолке |
| `submerged` | Под водой или другой жидкостью |

| Ключ | Для чего | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `type` | все | одно из распределений выше | `even` | Какое распределение |
| `center` | centered | int | середина диапазона высот | Высота, вокруг которой собирается |
| `range` | centered | int | половина диапазона высот | Насколько далеко от этой высоты достаёт |
| `smoothness` | centered | от 1 до 8 | `2` | Сколько бросков усредняется. Больше — уже полоса |
| `veinHeight` | sprawl | int | диапазон высот | Насколько высока одна жила |
| `veinDiameter` | sprawl | int | `12` | Насколько широка одна жила |
| `verticalDensity` | sprawl | от 1 до 100 | `16` | Насколько плотная по вертикали |
| `horizontalDensity` | sprawl | от 1 до 100 | `32` | Насколько плотная по горизонтали |
| `offsetMin` | terrain | int | `0` | Наименьшее смещение от поверхности |
| `offsetMax` | terrain | int | `offsetMin` | Наибольшее смещение от поверхности |
| `ceiling` | cavern | boolean | `false` | Крепиться к потолку пещеры, а не к полу |

```json
}
```

## Retrogen

Запись с `"retrogen": true` генерируется и в чанки, сохранённые до того, как вы её добавили. Каждый чанк записывает, что в нём уже было, так что дважды ничего не делается.

Флаг записи лишь помечает её как подходящую. Само догоняющее выполнение включается настройкой `retrogen`, которую пак может задать в своём блоке `settings`, а игрок — в конфиге; по умолчанию она выключена. Рядом с ней `adoptExistingChunks` решает, что делать при первой встрече со старым чанком. Включено — чанк помечается так, будто пак уже в нём отработал, и не догоняется никогда. Выключено — догоняется как любой другой. Включить `retrogen` при включённом `adoptExistingChunks` — значит не сделать ничего, потому что каждый старый чанк списывается раньше, чем попадёт в очередь. Чтобы заполнить существующий мир, включайте `retrogen` и выключайте `adoptExistingChunks` вместе.

```json
{
  "block": "mypack:ruby_ore",
  "size": 8,
  "attempts": 12,
  "minHeight": 8,
  "maxHeight": 48,
  "retrogen": true,
  "retrogenKey": "ruby_v1"
}
```

Смена `retrogenKey` в конфиге снова делает подходящими все чанки, а это добавляет новые жилы поверх старых, и плотность удваивается. Так и задумано, и именно поэтому ключ задаётся вручную.

## Предгенерация

Создание земли мира заранее, чтобы никто не генерировал чанки во время игры: ни лагов на чанках, ни неизвестного размера на диске — одно ожидание в начале вместо заикающегося первого часа. Включается паком через `pregenOnNewWorld` либо запускается вручную командой.

`/rdplserver pregen <radius>` создаёт каждый чанк в пределах стольких чанков от места запуска. `status` говорит, насколько всё продвинулось, `stop` завершает. `<radius> relight` прогоняет только проход освещения по уже существующей земле: обрабатывает швы, до которых прогон не дотянулся, и не трогает то, что никогда не создавалось.

Пока прогон идёт, всех удерживают. Игроков переводят в наблюдатели, оставляют на месте и показывают пульсирующую строку посреди экрана. Мир вокруг стоит на паузе. Режим, в котором пришёл игрок, записывается на него в момент удержания. Поэтому ни сохранение посреди прогона, ни падение игры, ни повторный вход не оставят никого наблюдателем. В конце прогона возвращается ровно тот режим, который был забран, либо `worldGameMode` пака, если он задан. О ходе сообщают каждую десятую часть пути, каждый прогон по завершении сам подсвечивает свой квадрат, а когда всё готово, игроков отпускают и приветствуют. Насколько далеко создано каждое измерение, сохраняется в мире, и завершённый мир прогон больше не запускает. Исключение одно: если файлы с землёй измерения пропадут с диска, это заметят и сделают его заново.

| Ключ | Что делает | Зачем задавать |
| --- | --- | --- |
| `pregenOnNewWorld` | Радиус в чанках, создаваемый вокруг точки появления сразу при создании мира. 0 — выключено. Любое число меньше 12 поднимается до 12: столько игра сама строит вокруг точки появления ещё до того, как запуск успевает начаться, и запуск, которому эта земля не принадлежит, ждёт, пока её осветят чанк за чанком | Единственный ключ, который включает предгенерацию для пака |
| `pregenDimensions` | Какие измерения создаются, по порядку, каждое вокруг своей точки появления | Добавить Нижний мир, Край или ваши собственные измерения |
| `pregenAllDimensions` | Каждое зарегистрированное измерение вместо списка, обычный мир первым | Сборки со многими измерениями. Считаются измерения всех модов, так что следите за объёмом |
| `pregenDimensionsWhenEntered` | Эти создаются, когда кто-то впервые в них ступит, снова удерживая всех до конца | Измерения, куда большинство игроков не заходит; кто не пойдёт, не платит ничем |
| `pregenToBorder` | Заполнять каждое измерение до его границы мира, а не по радиусу | Ограниченные миры |
| `pregenBorderLimit` | Насколько далеко может доставать граница, прежде чем прогон отклонят. Только конфиг, паку такой ключ недоступен | Защита от неуправляемого прогона; поднимайте, только понимая время и диск, которые это разрешает |
| `pregenResume` | Остановленный или прерванный прогон продолжается с того места, где встал. Измерение, центр и радиус прогона пишутся в сохранение при старте, поэтому падение, отключение питания или выход посреди прогона возобновляются при следующей загрузке примерно с той же точки, с точностью до десяти секунд. Прогон, остановленный намеренно, командой или сторожевым таймером, остаётся остановленным | Долгие прогоны на серверах; небольшие перезапускаются дёшево и без этого |
| `pregenKeepLoaded` | Сколько чанков держать загруженными позади прогона, чтобы соседи чанка были под рукой, когда его наряжают и освещают | Поднимите, если пересчёт света сообщает о многих чанках, отложенных на потом; стоит памяти |
| `pregenPauseAbove` | Прогон отдыхает, когда столько чанков ждут записи | Понизьте для медленного диска |
| `pregenMillisPerRound` | Сколько времени каждый тик может тратить на создание земли | Поднимайте на пустом мире, понижайте на сервере, где играют люди |
| `pregenRunningSays`, `pregenRelightSays`, `pregenFinishedSays`, `pregenStoppedSays` | Сообщения в чат для каждой стадии. Первые два могут содержать `%d` для процентов и после него `%s` для имени измерения либо `%1$d` и `%2$s`, чтобы поставить их в любом порядке, и всегда заканчиваются ` - ETA 00:00:00` для этого прохода, что настройкой не является. Завершение и остановка говорятся один раз, когда сделано всё запрошенное, и заканчиваются ` - Total time 00:00:00` для всего целиком, что тоже не настройка | Переписать их голосом вашего пака, назвать измерение, когда создаётся несколько, или заглушить |
| `pregenSpectatingSays` | Строка удержания посреди экрана, пока создаётся земля. Со значением по умолчанию говорит на языке каждого игрока; пустая не показывает ничего | Держите примерно до тридцати пяти символов, иначе в маленьких окнах обрежется |
| `welcomeSays` | Зелёное приветствие, показывается при каждом входе и после создания земли. Голая запись — строка для всех мест; запись `dimension=message` перекрывает её для этого измерения и заодно приветствует каждое прибытие туда, например `"-1=Welcome to the Nether!"`. Пустое сообщение после `=` заглушает это измерение; пустой список не показывает ничего. Со значением по умолчанию говорит на языке каждого игрока | Одна голая строка называет ваш пак; добавьте строки по измерениям, чтобы задать тон каждому миру. Держите строки примерно до тридцати пяти символов |

В паке всё это кладётся в блок `settings` [шаблона мира](#шаблоны-мира), как и любой другой ключ группы `chunks`. Вот они все, кроме `pregenBorderLimit` — он живёт только в конфиге:

```json
{
  "settings": {
    "pregenOnNewWorld": 63,
    "pregenDimensions": [0, -1],
    "pregenAllDimensions": false,
    "pregenDimensionsWhenEntered": [1],
    "pregenToBorder": false,
    "pregenResume": true,
    "pregenKeepLoaded": 2048,
    "pregenPauseAbove": 2000,
    "pregenMillisPerRound": 200,
    "pregenRunningSays": "Building your world, %d%% done",
    "pregenRelightSays": "Lighting your world, %d%% done",
    "pregenFinishedSays": "Your world is ready",
    "pregenStoppedSays": "World building stopped",
    "pregenSpectatingSays": "Spectating until the world is ready",
    "pregenWelcomeSays": "Welcome to Ruby World!"
  }
}
```

Прогоните это сами перед выпуском — от начала до конца и на том радиусе, который выпускаете. Число чанков растёт как квадрат радиуса. 63 в каждую сторону — шестнадцать тысяч чанков, 500 — больше миллиона, примерно по десять килобайт каждый. Честные числа для игроков — это папка region вашего тестового мира и часы на стене. Не выпускайте радиус, который ни разу не прогоняли.


### Поля

`field` не ставит ничего в точке и всё сразу. Вместо того чтобы выбрать место и построить вокруг него форму, оно задаёт вопрос каждому блоку в чанке между `minHeight` и `maxHeight` и ставит там, где ответ не ниже `threshold`. Это тот же вопрос, что задают группы твёрдости, поэтому оба описывают одни и те же жилы, и пак может собрать группу и запись, которые сходятся.

```json
{
  "block": "mypack:sulfur_ore",
  "replace": ["minecraft:stone"],
  "minHeight": 8,
  "maxHeight": 48,
  "shape": {
    "type": "field",
    "threshold": 0.6,
    "field": { "type": "speckle", "spread": 0.15 }
  }
}
```

| Ключ | Обязателен | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `threshold` | нет | от 0.0 до 1.0 | `0.5` | Насколько сильным должно быть поле, чтобы блок был поставлен |
| `field` | да | объект | нет | Тот же объект, что и у группы твёрдости, с теми же типами `speckle` и `seeded` |

Низкий `threshold` берёт почти всё поле и даёт широкие полосы, высокий берёт только середину каждого сгустка и даёт мелкие разбросанные карманы. С `speckle` выходит частая мелкая крапина, с `seeded` — более округлые сгустки или, если дать лучи, узлы с усиками, тянущимися друг к другу.

Как и пояс, поле не смотрит на `attempts` и `spread`, потому что его спрашивают по чанку, а не по попытке, и оно никогда не пишет в соседний чанк. Оно выводится из сида мира и собственного имени записи, поэтому один и тот же сид всегда даёт одни и те же жилы, а две записи с разными именами никогда не совпадают. `replace`, `adjacent`, `biomes` и климатические пределы работают как обычно.

### За счёт чего это быстро

Всё ниже — про «как», а не про «что»: инженерия, которая делает прогон быстрым, записанная, чтобы не потеряться. Паку ничего из этого не нужно, чтобы пользоваться ключами выше.

У создания земли свой быстрый путь для освещения, и он отходит в сторону, когда установлен движок света вроде Alfheim или Phosphor, отдавая работу ему. В обоих случаях вы получаете готовую, полностью освещённую землю.

Игра не станет освещать чанк, пока не существуют все восемь вокруг. А пока земля создаётся, те, что впереди, ещё не созданы. Осветить чанк прямо в момент создания почти никогда не выходит. Вместо этого при создании каждого чанка осматриваются девять вокруг этого места, и любой, чьё собственное кольцо теперь полно и всё ещё удерживается, освещается тут же.

Вычисляя свет, игра смотрит на шесть сторон блока и каждый раз просит список из шести направлений. Каждый запрос возвращает свежую копию одних и тех же шести. За создание мира это десятки миллионов копий списка, который никогда не меняется, и все они разом выбрасываются. Вместо этого используется один список.

Где хранится кольцо чанков, важно не меньше, чем то, что оно хранится. Искать его заново на каждое чтение, десятки миллионов раз, дороже части самих чтений. Оно лежит на самом мире, а это одно обращение к полю.

Считать, сколько занимает свет, само по себе заметно медленно. Спрашивать часы дважды на каждое из восьмидесяти миллионов распространений дороже, чем часть измеряемой работы. Поэтому считается каждое распространение, но замеряется одно из шестидесяти четырёх, а время масштабируется от них. Счётчики точные, а времена близкие.

Почти весь свет, который вычисляет игра, — это свет, который она уже знала. При создании чанка она проходит каждый столб от неба вниз и ставит полный дневной свет, пока не встретит твёрдую землю и ничего под ней. Затем обходит каждый открытый блок ниже и спрашивает, каким там должен быть свет. Под землёй и внутри камня ответ всегда «никакого», и он уже был «никакой», так что из каждой сотни таких вопросов едва два что-то меняют. Значение имеют только те, что рядом с входом в пещеру или под нависанием, где свет приходит сбоку.

Поэтому ответ вычисляется напрямую, до вопроса: сколько пропускает блок и сколько дневного света держит самый светлый из шести соседей. Это ровно то, до чего дошла бы сама игра, и там, где это совпадает с тем, что блок уже держит, делать нечего и вопрос пропускается. Дойти до этого ответа — несколько чтений из уже имеющихся под рукой чанков. Игра приходит туда же куда более длинным путём. Про лампы и огонь спрашивают как прежде, и освещено в итоге ничего иначе не будет.

Распространение света — самая медленная часть создания земли, и почти вся стоимость приходится не на свет. Каждый раз, читая яркость блока, его тип или видимость неба, игра заново ищет чанк с нуля. И делает это около шестнадцати раз на каждый рассматриваемый блок. За один прогон это заметно больше миллиарда поисков одних и тех же девяти чанков. Перед распространением света она ещё дважды спрашивает, вся ли земля вокруг на месте. И спрашивает снова на каждый блок.

Кольцо чанков вокруг освещаемого поэтому находят один раз, когда чанк берут в работу. Каждое чтение за этот проход обслуживается уже из него. Ответы те же, к каким пришла бы игра, только без похода за ними каждый раз. В самом свете ничего не меняется.

Это же означает, что свет ставится после деревьев, руды и озёр, а не до них. Сама по себе игра сначала освещает голую землю, а потом пересчитывает почти всё заново, пока наносится убранство. Двойная трата на землю, где ещё никто не стоит. Первый проход придерживают и делают только поздний — что при создании земли пачками, что когда игрок просто в неё заходит. Игра и так каждый раунд пробует снова на любом неосвещённом чанке. Придержанный чанк освещается раундом позже, вычисленный лишь однажды. Удерживаемые прогоном чанки заодно исключены из привычки игры пробовать свет на каждом чанке каждый раунд. Прогон знает, когда каждый из них готов, а попытка до этого может только провалиться. Чанк, до которого очередь так и не дошла, остаётся тёмным и освещает себя сам, когда к нему подойдут, и причин этому две, совсем разные. Первая: он стоит на самом краю запрошенного. В кольце вокруг него есть земля, которую никто не просил создавать и достроить уже нельзя. Это внешняя граница квадрата, и удержанием её не изменить. Другая — что он выпал из удерживаемого раньше, чем создались его соседи, и вот это удержание большего числа чанков как раз исправляет. Их считают отдельно, чтобы было понятно, где что.

Отдельная строка говорит, сколько раз каждое из этих сокращений не сработало и пришлось идти длинным путём. Считаются чанки, найденные всерьёз; блоки, опрошенные на состав; блоки, названные для записи. И отдельно — сколько раз генератору камня из Quark не пришлось читать мир ради земли, слишком далёкой от середины его скопления. Считаются только неудачи: считать удачи стоило бы дороже, чем они экономят.

# Управление

## Слой управления

Всё, что останавливает или меняет генерацию, разбито на группы, и у каждой группы есть один ключ в категории конфига `control` с тремя значениями:

| Значение | Что означает |
| --- | --- |
| `default` | Решает пак. Значения конфига — запасной вариант |
| `global` | Побеждает конфиг. Секции паков игнорируются |
| `off` | Группа выключена целиком, и никакой пак её не включит |

Группы: `ores`, `biomes`, `generators`, `structures`, `spawning`, `bedrock`, `voidWorld`, `recipes`, `terrain`, `entities` и `chunks`.

Настройки разрешаются в порядке **биом → шаблон мира → конфиг**. Блок `settings` шаблона мира использует те же имена ключей, что и конфиг, поэтому пак задаёт их так же, как задали бы вы:

```json
{
  "settings": {
    "monsterCap": 40,
    "flatBedrock": true,
    "worldGameMode": "creative",
    "oreWhitelist": ["minecraft", "mypack"],
    "pregenOnNewWorld": 63
  }
}
```

При управлении группой в положении `default` они побеждают, при `global` игнорируются, а при `off` вся группа не делает ничего, что бы ни говорил любой пак.

## Что делает каждая группа

### Ores

`blockOres` запрещает генерацию руды всем — и модам, и самому Minecraft, — кроме тех, что перечислены в `oreWhitelist`. `oreTypes` называет затрагиваемые типы руды, а `oreTypesAreBlacklist` задаёт направление: включено — перечисленные типы блокируются; выключено — генерируются только перечисленные. Достать можно только генерацию, идущую через событие генерации руды Forge. Это Minecraft и большинство модов, но не все. `blockOreDimensions` ограничивает блокировку руды определёнными измерениями, пустой список означает все, а `blockOreDimensionsAreBlacklist` превращает список в перечень измерений, оставляемых в покое. Измерение вне области действия не трогают вовсе. Руда другого мода спокойно генерируется там, пока обычный мир остаётся заблокированным.

### Biomes

`blockBiomes` и `biomeWhitelist` работают по модам, а `biomeNames` вместе с `biomeNamesAreBlacklist` — по именам. Заблокированные биомы заменяются на уже готовой карте биомов. Только так и добраться до океанов, грибных островов, разновидностей меза, джунглей, холмов и берегов: их выбирают вне списков, доступных моду. Заблокируйте все биомы — и обычный мир сам собой станет пустым. `blockBiomeDimensions` ограничивает всё это определёнными измерениями, пустой список означает все, а `blockBiomeDimensionsAreBlacklist` превращает его в исключение.

### Generators

`blockWorldGenerators` не даёт другим модам генерировать через их собственные генераторы мира. Именно так моды добавляют то, чего события Forge не видят: слизневые острова, пещерные кристаллы и подобное. `generatorWhitelist` сохраняет названные моды, `blockedGenerators` называет отдельные, а собственная генерация паков этого мода не блокируется никогда. `blockGeneratorDimensions` ограничивает это определёнными измерениями, а `blockGeneratorDimensionsAreBlacklist` инвертирует список.

`generatorTypes` блокирует по тому, что генератор делает, а не по тому, какому моду он принадлежит: `ores`, `structures`, `flora`, `lakes`, `terrain` либо `unknown` для неопознанных. `generatorTypesAreBlacklist` задаёт направление: включено — перечисленные типы блокируются; выключено — генерируются только перечисленные. Тип блокирует независимо от белого списка, ровно как это делает `oreTypes`, поэтому можно запретить всем модам добавлять руду, оставив их подземелья и деревья.

Тип берётся из имени класса генератора: его сверяют со встроенным списком слов для каждого типа. Большинство модов читается верно: `NetherOreGenerator` — это ores, `SlimeIslandGenerator` — structures. А генератор, названный ни о чём, вроде `SimpleGenHandler` у ProjectRed или `DEWorldGenHandler` у Draconic Evolution, выходит как `unknown`. `generatorTypeMap` исправляет такие вручную, по одной записи `pattern=type` на строку, где шаблон — это id мода или часть имени класса генератора:

```
mrtjpcore=ores
deworldgenhandler=structures
```

Сопоставленные записи проверяются раньше встроенных слов и исправляют в том числе неверно опознанный генератор. Включите `logBlockedGenerators` — и при первой блокировке каждый генератор попадёт в лог с присвоенным типом. Текущие счётчики по модам и типам покажет `/rdplserver generators`.

### Replacements

`blockReplacements` заменяет блоки в уже существующих чанках, по одной записи `block=block` на строку, с необязательными метаданными с любой стороны:

```
bigreactors:oreyellorite=minecraft:stone
mekanism:oreblock:0=minecraft:stone
tconstruct:ore:0=minecraft:netherrack
```

Каждый чанк обрабатывается один раз, при загрузке с диска, и помечается в своих данных, чтобы это не сделали дважды. Чанк, генерируемый впервые, чистится не сразу, а при следующей загрузке: пока он генерируется, соседние чанки ещё пишут в него. Чанк на краю освоенной земли чистится, но не помечается, поэтому его почистят снова, когда земля вокруг появится. `blockReplacementDimensions` и `blockReplacementDimensionsAreBlacklist` выбирают где. `blockReplacementMinHeight` и `blockReplacementMaxHeight` — полосу мира, в которую смотреть. А `blockReplacementKey` меняют, чтобы прогнать через это все чанки заново. Работает независимо от `retrogen`: мир, требующий уборки, обычно как раз тот, куда новые жилы добавлять не хочется. Заменяются только блоки. То, что мод сгенерировал как структуру, так не убрать: заменённый ею рельеф нигде не записан.

### Villages

Деревни используют те же списки `structure=value`, что и любая другая структура, под именем `villages`, так что до них достают `structureSpacing`, `structureMinDistanceFromSpawn`, `structureBiomes` и `structureBiomesAreBlacklist`. Список `structureBiomes`, если он не чёрный, ещё и добавляет названные биомы, которых в собственном списке структуры не было. Так деревни можно отправить в горы. Называйте биомы через registry name: добавлять умеют только они. Их шаг имеет нижнюю границу 9, потому что ваниль вычитает из него 8. `villagePieces` принадлежит той же группе, так что один переключатель охватывает и то, где стоят деревни, и то, из чего они построены. Группа `villages` отвечает только за добавленные паком участки.

`villagePieces` называет ванильные части деревни: `house1`, `house2`, `house3`, `house4garden`, `church`, `woodhut`, `hall`, `field1` и `field2`. Направление задаёт `villagePiecesAreBlacklist`. Можно убрать ванильные пшеничные поля, оставив дома, или перечислить только нужные части. Участки пака список не затрагивает: они добавляются сверху. Части из других модов — тоже, будь то дома Tektopia или участки Recurrent Complex: белый список убирает только ванильные части, так что, перечислив нужные ванильные, вы не удалите заодно чужие. Чтобы убрать часть из мода, возьмите чёрный список и назовите её, например `tekhouse2`.

### Blast Plaster

Что происходит после взрыва, из `blastplaster/*.json`. `default` отдаёт решение пакам, `global` не смотрит на файлы пака и оставляет поверх конфига Blast Plaster умолчания этого мода, а `off` полностью возвращает Blast Plaster его собственному конфигу.

### Structures

Ванильные структуры выключаются по имени, для каждого измерения. Размещением управляют четыре списка вида `structure=value`, по одному на строку. `structureSpacing` — насколько далеко друг от друга они засеваются. `structureSeparation` — ближайшее допустимое расстояние между двумя. `structureMinDistanceFromSpawn` — с какого удаления они начинаются. `structureBiomes` вместе с `structureBiomesAreBlacklist` — где им разрешено быть.

```
temples=24
monuments=40
mineshafts=200
```

```
temples=minecraft:desert,SANDY
monuments=minecraft:deep_ocean
```

Не каждая структура понимает каждую настройку. Шаг достаёт до храмов, монументов, особняков, городов Края и крепостей. Для `mineshafts` число означает один чанк из стольких, а не сетку: именно так их размещает ваниль. Разделение достаёт до монументов, особняков, городов Края и крепостей. Биомы достают до всех структур, кроме городов Края, потому что Край в этой версии — один биом и выбирать не из чего. Города Края всё равно сами выбирают место внутри сетки. Садятся они только на внешний остров, чья поверхность достаёт до y60. Увеличение шага их разрежает, но над пустотой не поставит. Крепости Нижнего мира сидят на фиксированной сетке, скрытой ванилью. До них достают только списки биомов и расстояния от точки появления. У деревень свои `villageSpacing`, `villageBiomes` и остальное.

`structureSpawns` заменяет порождаемых структурой мобов, что бы ни говорил биом вокруг; записывается как `structure=namespace:entity:weight:least:most`, через запятую:

```
netherbridges=minecraft:blaze:10:2:3,minecraft:wither_skeleton:8:5:5
temples=minecraft:witch:1:1:1
monuments=
```

Такой список в этой версии есть только у храмов, монументов и крепостей Нижнего мира. Деревни расставляют жителей из самих частей, а шахты, крепости и города Края обходятся спавнерами и расставленными мобами. Пустая строка после знака равенства, как у monuments выше, останавливает собственный спавн этой структуры.

`structureSpawners` говорит, кого порождает спавнер внутри ванильной структуры; записывается как `structure=namespace:entity`, через запятую для случайного выбора на каждый спавнер:

```
dungeons=minecraft:zombie,minecraft:husk
mineshafts=minecraft:cave_spider
netherbridges=minecraft:wither_skeleton
strongholds=minecraft:silverfish
```

Спавнер ставят четыре ванильные структуры: комната подземелья, коридор шахты, тронный зал крепости Нижнего мира и зал портала крепости. До каждой добираются отдельно — спавнеры, поставленные другими модами, не трогают никогда. Подземелья обычно выбирают из списка, куда моды добавляют через Forge. Упоминание их здесь забирает и этот выбор.

Шаг решает, где структура засевается, поэтому его изменение в уже существующем мире оставляет то, что там есть, и ставит новые по другой сетке.

### Spawning

Частота и пределы спавна мобов, по биомам. Спавн враждебных масштабируется через `surfaceDayMonsterRate`, `surfaceNightMonsterRate`, `undergroundDayMonsterRate` и `undergroundNightMonsterRate`. Каждый — множитель, где `1.0` это ваниль. Дневной спавн на поверхности можно выключить, не трогая пещеры. Пределы — это `monsterCap`, `creatureCap` для мирных животных, `ambientCap` для летучих мышей и подобного, `waterCreatureCap` для спрутов. Ванильные значения: 70, 10, 15 и 5. `-1` оставляет предел в покое.

### Посадка структур

`structureAdaptation` решает, к каким структурам подстраивается рельеф и как; записывается как `structure=mode`, например `"mansions=bury"`, `"monuments=none"`, и охватывает деревни, крепости, шахты, монументы и особняки. Режимов пять, те же, что в современных версиях: `none`, `bury`, `beard_thin`, `beard_box` и `encapsulate`. Деревни идут как `beard_thin`, если не переопределено, а всё остальное — как `none`, если не названо, что совпадает с тем, что современные версии выбирают сами. Храмы пока назвать нельзя, потому что они ставят себя только по мере постройки, и рельефу попросту не к чему подстраиваться вовремя.

### Посадка деревень

**Настройка экспериментальная и продолжает меняться.** Пользуйтесь на свой страх и риск. Она перекраивает рельеф прямо во время создания мира, поэтому всё, что она уложила, остаётся в этом сохранении навсегда, а ошибка в ней может оставить наполовину выровненную деревню или дорогу на насыпи. Пока над ней идёт работа, поведение меняется от сборки к сборке: два мира на одном сиде, созданные на разных версиях мода, не совпадут, а деревню из старой сборки новая не переделает и не починит. Если мир вам дорог, держите настройку выключенной или делайте резервную копию и помните, что деревни в нём — снимок того, что мод делал в день генерации этих чанков.

`terrainAdaptation` переделывает то, как деревни выбирают землю и садятся на неё; перенесено по духу из того, как современные версии сажают свои структуры, и доведено дальше. Деревня закладывается только в чанке, где земля меняется не больше чем на десять блоков, и никогда ближе восьми чанков к другой деревне; области, где такого чанка нет, не закладывают ничего. Колодец садится на самую низкую землю, которой касается его собственное основание, и вся деревня смещается вместе с ним, так что всё остальное выравнивается уже от него. Дороги планируются по мере укладки. Поверхность следует самой низкой естественной земле по всей ширине дороги: бугры срезаются, ямы засыпаются. Уклон не превышает одного блока на шаг, а короткие провалы перекрываются досками. Покрытие дороги подбирается под землю, по которой она идёт: тропинки по земле, песчаник по песку, обожжённая глина в меса, гравий по камню и по гравию, доски над водой. Деревня в пустыне получает песчаниковые улицы вместо просёлка, и дороги больше не пропадают там, где земля не трава. Там, где две дороги пересекаются, они сходятся на меньшей из двух высот: только высота, до которой дотягиваются обе, не оставляет между ними ступени. Каждая постройка садится на блок выше дороги, к которой обращена. Уровень берут с уже уложенной дороги либо предсказывают, на какую землю она ляжет. Ступени у порога поэтому лежат на поверхности дороги, а дверь стоит за ними. Постройка, под которой где-либо понадобилось бы больше двух блоков подсыпанной земли, здесь не строится: она сдвигается вдоль дороги до двенадцати блоков в поисках самой пологой посадки и снимается совсем, если такой нет. Деревни на изломанной земле выходят реже, зато без построек на постаментах. Кольцо вокруг постройки подсыпается со стороны склона вниз и срезается со стороны вверх, ещё на блок мельче кольцом дальше. Фермы сохраняют ванильный уровень земли. Фонарные столбы стоят на высоте дороги, которую освещают, а не обочины рядом, и под ними досыпается земля там, где дорога идёт выше обочины; ванильные факельные столбы в план не попадают, потому что эти их заменяют. Земля под каждой постройкой досыпается до ближайшей опоры тем же материалом, на котором постройка стоит. Стены и дверные проёмы прорезаются в склонах, земля снимается с крыш. Любое дерево, стоящее в постройке, срубается целиком: листва уходит вместе со стволом, но листва уцелевшей ветки остаётся при ней. Особняки и разбросанные постройки (храмы, хижины, иглу) держат к тому же требованию ровной земли, прежде чем им позволят встать. Это переделывает сам рельеф по ходу создания. Мир, сгенерированный с включённой настройкой, отличается от сгенерированного без неё — то же предупреждение несут и современные версии. По умолчанию она выключена, пока пак или конфиг не попросят.

### Bedrock

`flatBedrock` заменяет неровный слой ровными, по измерениям и по биомам, с блоком-заполнителем на ваш выбор. `flatBedrockRetrogen` делает то же с уже существующими чанками. Отменить это нельзя: исходный узор нигде не записан. `bedrockLayers` задаёт, сколько слоёв остаётся. `flatBedrockRoof` делает и потолок там, где он у измерения есть. `flatBedrockFiller` — то, чем заменяется убранный бедрок: оставьте пустым, чтобы выбирать по измерению, либо назовите свой для каждого через `flatBedrockFillers`. Каких измерений и биомов это касается, задают `flatBedrockDimensions`, `flatBedrockBiomes` и `flatBedrockBiomeTypes`, а `flatBedrockDimensionsAreBlacklist` и `flatBedrockBiomesAreBlacklist` превращают эти списки в исключения.

### Замедление вдали

Сущности стоят серверу дороже всего остального, и большинство из них далеко от любого игрока. `slowDistantEntities` даёт чанку без игрока в пределах `slowDistance` блоков один тик из `slowRate`. Всё в нём по-прежнему движется, плавает, горит и исчезает — только медленнее. Без тиков не остаётся ничего.

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `slowDistantEntities` | нет | boolean | `true` | Замедляется ли вообще что-нибудь |
| `slowedKinds` | нет | список из `items`, `experience`, `projectiles` | `{items, experience}` | Каким видам достаётся меньше тиков. Всё, что думает само, замедляется иначе и здесь не называется. Машины не замедляются никогда |
| `slowDistance` | нет | int, от 64 | `192` | На каком удалении от ближайшего игрока чанк замедляется |
| `slowRate` | нет | int, от 1 до 20 | `4` | Один тик из стольких достаётся замедленному чанку. `1` не замедляет ничего |
| `neverSlowed` | нет | список имён сущностей | нет | Их не трогают, как бы далеко они ни были |
| `slowRecheck` | нет | int, от 1 до 100 | `20` | Как часто заново вычисляется расстояние до ближайшего игрока |

Всё, что думает само, обрабатывается иначе и в `slowedKinds` не называется вовсе. Это любой моб, животное, житель и голем, из какого бы мода он ни был. Тиков ему не урезают никогда, потому что игрок может увидеть, как он идёт. Вместо этого он тикает каждый тик, но думает реже. Ту часть его разума, что решает, чем заняться дальше, — она же и самая дорогая, — спрашивают один раз из `slowRate`, а не каждый третий тик. Он так же движется, падает, тонет, горит и прокладывает путь, просто реже меняет решение, пока рядом никого нет. Смотреть тут не на что: ни шагов рывками, ни догоняния. Тот, к кому игрок подойдёт, вернётся к обычному себе раньше, чем попадёт в поле зрения. Раз это нельзя заметить, это и не выбор: происходит везде, где замедление включено вообще.

То, чему урезают тики, всё равно стареет обычным темпом. У выброшенного предмета и у сферы опыта свой счётчик исчезновения. Его двигают даже в тот тик, который замедленный чанк не берёт. Так что предмет по-прежнему лежит на земле пять минут, а не двадцать. Уменьшается только то, что он делает каждый тик, но никогда не то, сколько он живёт.

Намеренно удерживаемый чанк не замедляется никогда, как бы далеко он ни был. Это чанки, которые держит чанклоадер. Весь смысл его держать — чтобы внутри всё продолжало работать. Ферма, оставленная без хозяина, работает в расчётном темпе. Чанки вокруг точки появления мира к ним не относятся, потому что их никто не просил, поэтому они замедляются как везде.

Чанк замедляется или не замедляется целиком, поэтому то, что внутри, ведёт себя как должно: предметы падают в ту же кучу, моб по-прежнему идёт за соседним. Каждый игрок считается сам за себя, поэтому у того, кто ушёл в одиночку, вокруг остаётся тихое место, где бы он ни был. Кое-что оставляют в покое, как бы далеко оно ни было: то, на чём едут, что названо, приручено, на поводке, светится, защищено от исчезновения, под эффектом или уже гонится за игроком. Машины — тоже. Это касается любого мира, включая добавленный модом.

### Наблюдение за работой с чанками

При включённом `worldgenDebug` строка каждые сто раундов говорит, на что мир тратит работу с чанками. Сколько чанков создано с нуля и сколько пришлось вернуть после того, как их отпустили. Сколько из возвращённых пришло с диска, а не из очереди, ещё ждущей записи. Сколько файлов регионов открывалось и как часто их закрывали все разом. И наибольшее число удерживаемых чанков и незавершённых записей за всё время. Всё это написано ради одного вопроса: где генерация земли тратит время — в самой генерации или в возвращении той же земли обратно. Включайте перед большой предгенерацией и выключайте после.

За ней идут ещё три строки. Одна про запись чанков в хранилище, одна про их освещение. Третья разделяет создание самой земли на грунт, убранство от игры и убранство от каждого мода, с названными худшими пятью. Тогда медленный мир читается как четыре отдельные статьи расходов, а не одна, и ответственный мод называется, а не угадывается.

### Создание земли заранее

Достаточно велико, чтобы иметь собственный раздел, см. [Предгенерация](#предгенерация).

### Блоки, ждущие своей очереди

Растекание воды, застывание лавы и рост посевов — всё это блоки, которые чего-то ждут, прежде чем сработать. Игра держит их в одной куче. При каждой записи чанка она проходит эту кучу от края до края в поисках тех немногих, что принадлежат ему. Чем больше их в мире, тем медленнее каждая запись — даже если в записываемом чанке их нет вовсе. Теперь они отсортированы по своему чанку. Сортировка выбрасывается и делается заново, как только куча меняется или раунд идёт дальше. Запись чанка смотрит лишь на горстку вокруг.

### Запас для блоков в чанке

Чанк хранится срезами, и каждый срез держит список видов блоков в нём, начиная с места на шестнадцать. Переход за шестнадцать означает создание списка побольше и копирование всех четырёх тысяч блоков среза, потом снова на тридцати двух и снова на шестидесяти четырёх. Земля с несколькими сортами камня и руды проходит все эти пороги, поэтому это делается четырежды ради небольшого запаса. Теперь при первом же переполнении берётся сразу самый крупный из этих размеров: одно копирование вместо четырёх, ценой нескольких килобайт на срез, который через мгновение и так пойдёт в дело.

### Подготовка чанков к записи

Прежде чем записать чанк, его переводят в дисковую форму. Это проход по каждому блоку с поиском каждого в таблице по имени. Земля идёт длинными участками одного и того же, и один поиск повторяется тысячи раз ради одного камня. Теперь ответ на предыдущий сохраняется и берётся снова, если следующий блок тот же. Выключить это нельзя, потому что взвешивать нечего: ответ в обоих случаях один и тот же.

### Запись чанков

Игра пишет готовые чанки в собственном потоке, по одному, отдыхая сотую долю секунды после каждого. Это держит её примерно на сотне чанков в секунду, каким бы быстрым ни был диск. Пока кто-то играет, этого достаточно. Пока земля создаётся пачками — близко не достаточно, и незаписанные чанки копятся в памяти. `hurryWritesAbove` говорит, сколько может ждать, прежде чем она перестанет отдыхать и начнёт писать так быстро, как может. `100` — значение по умолчанию, совпадающее с точкой, где игра сама начинает придерживать генерацию; `0` оставляет отдых всегда, как делает игра. Пока ждущих немного — а это каждый обычный момент игры, — не меняется ничего.

На каждую уборку мусора пишется своя строка: какой сборщик отработал, сколько занял, сколько было занято до и после и сколько места у игры было на тот момент. Если это место меняется, об этом говорят: рост места сам по себе и вызывает самые долгие из этих пауз. Игра, запущенная с меньшим местом, чем ей в итоге нужно, будет останавливаться ради его наращивания снова и снова — в моменты, никак не связанные с тем, чем она занята. Запуск с максимально разрешённым местом избавляет от этого полностью.

Последняя строка говорит, сколько рабочего мусора выброшено с прошлого раза, сколько заняла уборка и во сколько проходов. И какую долю разрешённого места игра держит сейчас. Создание земли по своей природе выбрасывает очень много: каждый чанк перед записью превращается в свежие массивы. Уборка идёт между раундами, а не во время них, и потому проявляется как рывок, а не как время в счётчиках выше.

### Чанки точки появления

Игра держит чанки вокруг точки появления загруженными независимо от того, есть там кто-то или нет: модам нужно место, которое тикает всегда. Это 128 блоков в каждую сторону, около 289 чанков, и в самой игре это не настраивается. `spawnChunkRadius` задаёт это расстояние. `128` — то, что делает игра, и значение по умолчанию; меньшее число держит меньший якорь, а `0` не держит ничего, так что область появления выгружается как любая другая. `spawnChunkRadii` задаёт радиус для отдельного измерения, записью `dimension=blocks`, по одной на строку, и перекрывает `spawnChunkRadius` для названных измерений.

Держит их только измерение, зарегистрированное как хранящее свою точку появления, а в самой игре это лишь обычный мир: ни Нижний мир, ни Край их никогда не держали, так что задавать им это бессмысленно. Измерение, добавленное модом, держит их, только если мод об этом попросил, а мод, который попросил, часто тащит вторые 289 чанков, которых пак никогда не хотел. Остаётся ли мир загруженным вообще — отдельная вещь, которой это не касается: измерение, помеченное модом как остающееся загруженным, остаётся загруженным и при `0`, оно просто перестаёт держать чанки. Большинству модов, использующих точку появления как якорь, нужно, чтобы там что-то было, а не 289 чанков этого, так что небольшое число обычно оставляет их работать, а `0` нет.

### Пустой мир

`voidWorld` генерирует пустой мир с площадкой в точке появления. Мобы, животные, структуры и всё, что иначе сгенерировал бы мод, останавливаются. Блок, размер и высота площадки — это `voidPlatformBlock`, `voidPlatformSize` и `voidPlatformHeight`; размер округляется вниз до нечётного числа блоков, чтобы площадка стояла по центру точки появления. `voidWorldDimensions` выбирает, какие миры опустошаются, по умолчанию только обычный, а `voidWorldDimensionsAreBlacklist` превращает список в тот, что надо оставить в покое. Нижний мир и Край опустошаются так же, как обычный. Неважно, те ли это, что строит эта версия, или те, которыми их заменил мод. Площадка даётся только обычному миру — путь в опустошённый Нижний мир или Край пак обеспечивает сам. В опустошённом Крае нет ни дракона, ни кристаллов, ни фонтана из бедрока: бой, который их строит, так и не начинается.

### Дракон

`dragonFight` принадлежит группе `structures` и решает, происходит ли всё это вообще. Дракон, его полоса, кристаллы, фонтан под ним и возрождение, которое игрок запустил бы кристаллами Края. Опустошённый Край обходится без него, пока пак не попросит, а обычный Край его имеет, пока пак не скажет иначе, так что `dragonFight` стоит задавать в обе стороны.

### Terrain

`worldType` решает, каким будет новый мир, что бы ни выбрали на экране создания: `default`, `largebiomes`, `amplified`, `customized` или добавленный модом вроде `biomesop` или `realistic`. Пак, построенный вокруг одного типа мира, называет его здесь, и каждый новый мир создаётся таким. Пусто, значение по умолчанию, оставляет выбор тому, кто создаёт мир. Уже существующий мир сохраняет свой тип, а незнакомое имя попадает в лог и игнорируется. `worldTypeExceptions` называет выборы, которые остаются в силе, — для начала плоский мир и отладочный, — потому что пак, которому нужен один тип мира, редко хочет отнять суперплоский у того, кто что-то тестирует; а тому, кто создаёт мир, в чате, уже внутри, сообщают, что тип выбрал пак. Это сообщение решает конфиг через `tellWorldType`, а не пак, поэтому играющий может выключить его для себя, и никакой пак не включит обратно. При смене типа настройки, с которыми создавался мир, отбрасываются: писались они под прежний тип.

`worldSeed` решает, с каким сидом создаётся каждый новый мир, что бы ни набрали на экране создания. Пишется так же, как набирался бы: число используется как есть, а всё остальное превращается в число тем же способом, каким игра превращает слово в число, поэтому и `Hollow Ridge`, и `-4172144997902289642` допустимы и оба всегда дают один и тот же мир. Пусто, значение по умолчанию, оставляет выбор тому, кто создаёт мир. Уже существующий мир сохраняет сид, с которым создан, поэтому это решает только то, что достанется новому. Пак, построенный вокруг одной карты, называет её сид здесь, и каждый мир, созданный с этим паком, — эта карта.

`generatorOptions` формирует сам обычный мир: уровень моря, лавовые океаны и все шумы рельефа, в том же формате, который пишет тип мира customized. Применяется к миру при создании и никогда после, поэтому уже существующий мир остаётся ровно таким, каким был. Мир, уже несущий собственные настройки, их сохраняет, а лог называет использованную строку.

Тип мира, который несёт собственные настройки и никогда не смотрит на настройки мира, — как делает realistic у Quark, — получает настройки пака, влитые в собственные, поэтому форма, ради которой он строился, сохраняется, пока пак не попросит другого.

`terrainWorldTypes` называет типы мира, которым настройки отдаются вообще: `default`, `customized`, `biomesop`, `realistic` и так далее, а `terrainWorldTypesAreBlacklist` превращает это в список тех, кого надо оставить в покое. Пусто, значение по умолчанию, означает все типы мира. Пак, который формирует обычный мир, но хочет оставить тип мира от мода ровно таким, каким мод его сделал, называет его здесь — и на этом всё: ничего не вливается, ничего не передаётся, а собственный экран настройки мода остаётся открытым. Имена сверяются с тем типом мира, с которым мир был создан, так что названный здесь несуществующий тип, просто никогда не совпадёт и ничего не стоит.

Всё сказанное ниже про Biomes O' Plenty происходит только при установленном этом моде, потому что работу делает совместимость, которая грузится только при его наличии. Без него нет и типа мира `biomesop`, чтобы его выбрать, а пак, который его называет, остаётся с тем типом мира, с которым мир на самом деле создан.

В мире Biomes O' Plenty те же настройки переводятся в слова, которые читает этот мод — второй их копии паку не нужно. `biomeSize` становится одним из его пяти размеров, настройки шума и масштаба проходят как есть, а всё, чего он не читает, опускается со строкой в логе об этом. Этот мод читает намного меньше, чем тип мира customized, и вообще никогда не читает из своих настроек уровень моря, пещеры, озёра и переключатели структур — их передают ему напрямую, а пак задаёт их так же, как для любого другого мира.

Две вещи он решает сам. Реки выходят из его собственных слоёв и настройки не имеют, поэтому `riverSize` там ничего не значит. И где на самом деле сидят океаны, горы и области — это тоже его слои, достижимые только через `landScheme`, `tempScheme`, `rainScheme` и `biomeSize` — пак формирует тот мир в терминах того мода, а не типа мира customized. Мир из одного биома паку по-прежнему доступен: заблокируйте все биомы и назовите нужный как `default` шаблона — это работает на его типе мира так же, как на любом другом.

Всё остальное, что делает пак, — блокировка биомов и руды, замена блоков, ровный бедрок, размещение структур, собственная генерация, — через эту строку не проходило вовсе и работает одинаково на любом типе мира.

### Логирование

`logBlockedOres`, `logBlockedBiomes`, `logBlockedRecipes` и `logBlockReplacements` каждый раз записывают в лог первый случай, когда что-то отвергли, чтобы вы видели, что правило блокировки на самом деле поймало, а не гадали по тому, чего не хватает. Это первое, что стоит включить, когда правило вроде бы не делает ничего или делает слишком много.

### Recipes

`blockRecipes` и `blockFurnaceRecipes` удаляют всё, кроме модов из их белых списков. По умолчанию не освобождён никто, так что впишите пространство имён собственного пака, чтобы сохранить его рецепты. Добавления CraftTweaker и GroovyScript выживают всегда, что бы ни говорил белый список. Белые списки — это `recipeWhitelist` и `furnaceWhitelist`; `blockedRecipeMods` и `blockedFurnaceMods` работают в обратную сторону и удаляют рецепты названного мода, что бы ни говорил белый список. `recipeMatch` решает, откуда читается id мода при блокировке рецептов крафта: из имени самого рецепта или из того, что он производит.

## Universal Tweaks

Universal Tweaks меняет несколько тех же ванильных блоков и поведений, что и этот мод. Там, где они пересекаются, этот мод уступает и отдаёт дело Universal Tweaks, вместо того чтобы оба правили один метод, оставляя результат на усмотрение того, кто загрузился последним. Каждый раз об этом пишется в лог с указанием, что именно опущено.

| Что пересекается | Когда этот мод отходит в сторону |
| --- | --- |
| `promptLeafDecay` | У Universal Tweaks включён `Fast Leaf Decay` |
| `lenientPaths` | У Universal Tweaks включён `Lenient Paths` |
| `cactusMaxHeight` | Universal Tweaks установлен |
| `caneMaxHeight` | Universal Tweaks установлен |
| Возврат через портал в Нижний мир | Universal Tweaks установлен |

Первые два читают собственные переключатели Universal Tweaks из `config/Universal Tweaks - Tweaks.cfg`, поэтому, выключив один там, вы возвращаете эту работу сюда. У пары высот такого переключателя нет, есть только `Cactus Size` и `Sugar Cane Size`, поэтому этот мод отходит в сторону всегда, когда Universal Tweaks присутствует вообще, а высоту вы задаёте там.

**Возврат через портал в Нижний мир** — единственное, у чего с этой стороны нет настройки. Без него, идя обратно через портал в Нижний мир, вы попадаете к тому порталу, который найдёт ванильный поиск, а после достаточного количества путешествий это часто не тот, из которого вы вышли. Этот мод запоминает, где вы вошли в Нижний мир, и возвращает вас туда. У Universal Tweaks своя обработка, поэтому при его установке это пропускается целиком.

**Ничто из этого не касается пака.** Всё выше — про собственные кактус, тростник, листву, тропинки и порталы Minecraft. Блоки, описанные вашим паком, несут собственное поведение, а порталы пака в `portals/*.json` — отдельная система, которую Universal Tweaks не видит вовсе.

## CoFH World

Моды, требующие CoFH World, загружаются без него: требование снимается автоматически, кроме модов, которые действительно вызывают его API и упали бы.

Их собственная генерация при этом не происходит, потому что читает их `assets/<modid>/world/*.json` именно CoFH World. Ожидается, что это покроет пак.

Если этого нет, `readCofhWorldFiles` читает те файлы прямо из jar модов и генерирует их через этот мод. По умолчанию выключено, и отходит в сторону, когда установлен настоящий CoFH World, который тогда генерирует как обычно. Преобразуется каждый генератор и каждое распределение CoFH, которые что-либо производят, — они переносятся на формы и распределения выше. Формы здесь собственные, поэтому озеро или шпиль не будут выглядеть в точности так же. Взвешенные списки структур, таблицы поворота и отражения, списки игнорируемых блоков и сужение сталагмитов переносятся полностью. Сужение подобрано по форме, а не по формуле, поэтому очертание шпиля близко, но не идентично.

Перевод этих файлов в пак — поддерживаемый путь и единственный способ изменить то, что они генерируют.

## Lost Cities

Lost Cities заменяет генератор обычного мира собственным, поэтому всё, что встроено в обычный генератор, на его мирах перестало бы работать. Совместимость, которая загружается только при установленном Lost Cities, переносит три вещи:

- `generatorOptions` формирует землю между городами и под ними. Lost Cities читает только настройки шума, поэтому уровень земли, уровень воды, пещеры, озёра и переключатели структур берутся из его собственных профилей, а `seaLevel` на его мирах не делает ничего; сводка в логе об этом говорит. `terrainWorldTypes` ограничивает его как любой другой тип, по имени `lostcities`.
- Пустой мир работает, включая тот, что даёт полностью заблокированный список биомов. Города и земля исчезают вместе, а платформа и точка появления ведут себя так же, как везде.
- `stoneBlock` биома из пака заменяет камень под ним, на каждом типе ландшафта Lost Cities: обычном, парящем, космическом и пещерном.

Сами города — не дело этого мода. Насколько они большие и частые, из чего построены здания, уровни земли и воды — всё это лежит в собственных файлах профилей Lost Cities в `config/lostcities`, а его JSON зданий идёт через его собственную настройку `assets` там же. Пак, который поставляет мир Lost Cities, кладёт эти файлы рядом с собой, так же как кладёт конфиг любого другого мода.

`worldType` со значением `lostcities` делает каждый новый мир миром Lost Cities, так же как делает его `biomesop` или `realistic`. Принудительный тип сбрасывает настройки, которые мир бы нёс, поэтому мир попадает на профиль Lost Cities по умолчанию, а какой это профиль, называет `defaultProfile` в `config/lostcities/general.cfg`. И наоборот: пак, принуждающий другой тип, отнимает Lost Cities у игрока, который его выбрал, поэтому пак, который хочет оставить этот выбор за игроком, добавляет `lostcities` в `worldTypeExceptions`.

Всё остальное через генератор и не шло и работает как везде: генерация пака, блокировка руд и биомов, шаг структур и их спавнеры, плоский бедрок, retrogen, предгенерация, а его два сундучных лут-стола переопределяются и дополняются как любые другие.

## Интеграция с Blast Plaster

Взрывы оставались последним, чего пак не мог описать. Всё прочее в облике мира — файл в этой папке, а вот что останется после крипера, задавал тот мод, которому это досталось. Сложную половину задачи Blast Plaster решил давно: собрать воронку обратно блок за блоком и при этом понимать, где кончается одно дерево и начинается другое. Вместо того чтобы писать это заново, мод опирается на него и поставляет его как зависимость.

Выигрыш — управление, которого у него самого нет. Blast Plaster читает один конфиг на всю игру; под управлением пака он отвечает по измерениям: верхний мир может хранить свои шрамы, пока Нижний зарастает у вас за спиной, и пак привозит это решение с собой, а не отправляет игроков править конфиг. Та же работа окупается и там, где не ждёшь: вырубка деревьев в деревнях пользуется геометрией деревьев из Blast Plaster, поэтому дерево, нависшее над новой дорогой, падает целиком, а не срезается по границе.

Установленный сам по себе, Blast Plaster работает от собственного конфига ровно как раньше. Этот мод берётся за руль только тогда, когда об этом просит пак.

Файлы лежат в `assets/<namespace>/blastplaster/*.json`. Ключи, написанные наверху файла, действуют везде; блок `dimensions` переопределяет их для одного измерения по его id. Всё, чего пак не назвал, остаётся таким, как сказано в собственном конфиге Blast Plaster, так что пак задаёт ту горстку, которая ему важна, и остального не трогает.

```json
{
  "explosionMode": "EJECT_DROPS",
  "healFullTrees": true,
  "maxTreeSize": 400,
  "dimensions": {
    "-1": { "explosionMode": "HEAL", "minimumTicksBeforeHeal": 200 },
    "1": { "enableExplosionSmoke": false }
  }
}
```

`explosionMode` задаёт форму всему остальному. `HEAL` выбивает блоки, а потом собирает мир обратно, `EJECT_DROPS` оставляет воронку и роняет примерно треть того, что там было, — так ведёт себя крипер в нетронутой игре, — а `VISUAL_TOSS` оставляет воронку и не роняет ничего. Когда управляет этот мод, по умолчанию стоит `EJECT_DROPS`, а не собственный `HEAL` мода Blast Plaster: пак, который поставил оба мода и не написал ничего, получает взрывы, которые ведут себя так, как в знакомой игроку игре. Тот, кто хочет, чтобы мир чинил себя сам, просит `HEAL` — везде или в одном измерении.

| Ключ | Значение | Что делает |
| --- | --- | --- |
| `explosionMode` | `HEAL`, `EJECT_DROPS`, `VISUAL_TOSS` | Что происходит после хлопка |
| `healCreepers`, `healNonPlayerTNT`, `healWither`, `healAll` | true или false | Какие взрывы вообще обрабатываются |
| `processPlayerIgnitedTNT` | true или false | Обрабатывается ли вместе с остальными динамит, подожжённый игроком |
| `customEntitiesToHeal` | список имён сущностей | Взрывы из других модов, названные как `modid:entity` |
| `healFullTrees` | true или false | Задетое взрывом дерево берётся или восстанавливается целиком, а не перерубается пополам |
| `maxTreeSize` | число | Сколько блоков дерево вправе забрать себе, прежде чем его оставят в покое |
| `minimumTicksBeforeHeal`, `randomTickVar` | числа | Через сколько начинается починка и насколько неровно она идёт |
| `overrideBlocks` | true или false | Переписывает ли починка то, что успели построить в воронке |
| `enableFakeTossedBlocks` | true или false | Обломки, вылетающие из взрыва |
| `enableExplosionFlash` | true или false | Яркая вспышка в момент взрыва |
| `explosionFlashDuration`, `explosionFlashLightLevel`, `explosionFlashParticleCount`, `explosionFlashPulses` | числа | Сколько держится вспышка, насколько ярко горит, сколько частиц бросает и сколько раз пульсирует |
| `enableExplosionSmoke` | true или false | Столб дыма после взрыва |
| `explosionSmokeDuration`, `explosionSmokeParticleCount` | числа | Сколько держится дым и насколько он густой |
| `playerTNTAlwaysDrops`, `playerTNTDropFullBlocks` | true или false | Что оставляет после себя динамит самого игрока |
| `enableDropSuppression`, `dtSpecialDrops` | true или false | Дроп внутри взрыва и собственный дроп Dynamic Trees |
| `preventMobDrops` | true или false | Падает ли что-нибудь с мобов, убитых взрывом |

**Ваниль на вид.** Пак, чьи взрывы никто не должен отличить от нетронутой игры, пишет `EJECT_DROPS` и выключает `healFullTrees`, `enableFakeTossedBlocks`, `enableExplosionFlash`, `enableExplosionSmoke`, `preventMobDrops` и `playerTNTAlwaysDrops`. Всё прочее — это Blast Plaster, открывающий карты, и каждый из этих ключей можно задать и по измерениям, так что обычный мир будет выглядеть нетронутым, пока другое измерение чинит себя само.

**Игроки без мода** в обоих случаях не увидят ничего необычного. Вспышка — единственное, что ставит в мир собственный блок, поэтому, когда пак задаёт `vanillaClients`, её выключают, что бы ни было написано в файле, а всё остальное — это частицы и предметы, понятные и голому клиенту.

Две настройки Blast Plaster ключами пака не являются: его отладочный лог и список, который сводит каждое бревно с его листвой. Именно эта пара говорит моду, что дерево — это дерево, и здесь, и там, поэтому она остаётся одним ответом на всю игру, а не разным в каждом измерении. Обе живут в собственном конфиге Blast Plaster.

# Описание нового контента

## Как работают описания

Рядом с папками, которые переопределяют файлы, есть папки, которые описывают новое. Путь и есть личность: файл `assets/mypack/blocks/ruby_ore.json` регистрирует блок с именем `mypack:ruby_ore`.

Регистрация происходит с самым низким приоритетом, какой предлагает Forge, поэтому, если настоящий мод регистрирует то же имя, побеждает мод, а ваш файл игнорируется. Ничто здесь не может заменить мод.

**Где проходит граница.** Всё, чему нужны tile entity, GUI, инвентарь или собственная логика на каждый тик, требует настоящего мода. Всё, что не доходит до этого, — честная игра.

### Ваше пространство имён — это ваш мод

Имя, которое вы выбираете, во всех практических смыслах является id мода. Ничто не грузится как мод и в списке модов никогда не появляется, но всё, что читает id мода, читает ваше:

- Registry names выглядят как `mypack:ruby_ore`, ровно как у мода, и записываются в каждый сохранённый мир, где они есть.
- Белые списки руды, биомов, генераторов и рецептов в конфиге совпадают с ним, поэтому `oreWhitelist = mypack` сохраняет вашу руду и блокирует чужую.
- `/rdpl which`, `/rdplserver oregen` и все отчёты группируют по нему.
- JEI, словарь руд и поиск других модов видят его так же.

Поэтому выберите одно имя в начале и не меняйте его никогда. Переименование пространства имён осиротит всё уже поставленное в мире, ровно как смена id у мода. Для починки этого и существует `registry_remap`.

Работает это в обе стороны: `requires` принимает пространство имён пака так же охотно, как id установленного мода, поэтому один пак может зависеть от другого и пропускаться, когда того нет.

**Отсутствующий мод останавливает игру, ровно как собственная зависимость мода.** Каждый id мода из любого `requires` в ваших паках передаётся Forge как зависимость этого мода ещё до всякой загрузки. Если он не установлен, вы получите стандартный экран Missing Mods с перечислением нужного — и на клиенте, и на выделенном сервере, — а пока ничего не генерируется и не регистрируется.

Отсутствующий *пак* — другое дело. Пространства имён паков не моды и до этой проверки не доходят. Описание пропускается, в `logs/rdpl.log` уходит строка с указанием, чего не хватило, и игра идёт дальше. Если ожидаемого блока нет в творческой вкладке, эта строка лога — первое, куда стоит посмотреть.

`requires` принимает только голые id. Синтаксиса диапазонов версий нет, поэтому он может сказать, что мод должен присутствовать, но не какой версии.

Два собственных id мода, `resourcedatapackloader` и `resourcedatapackloader_mixin`, зарезервированы. Описание контента под ними игнорируется и попадает в лог: это было бы притязанием на то, что регистрирует сам мод. Переопределять ресурсы этого мода по-прежнему можно, нельзя только регистрировать там контент.

Все таблицы ниже устроены как в разделе [Как писать JSON](#как-писать-json): обязателен ли ключ, что в нём может лежать и что будет, если его не писать.

Почти все описания принимают ещё и `requires` — список id модов или пространств имён паков, которые должны присутствовать, иначе файл пропускается.

### Ключи варианта

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `meta` | да | от 0 до 15 |, | Значение метаданных, которое занимает этот вариант |
| `hardness` | нет | float | `1.0` | Сколько времени ломается. У обсидиана `50`, `-1` — неразрушимо |
| `resistance` | нет | float | `5.0` | Сопротивление взрыву |
| `light` | нет | от 0 до 15 | `0` | Излучаемый свет |
| `harvestLevel` | нет | от 0 до 3 | значение файла | Переопределяет уровень инструмента для этого варианта |
| `rarity` | нет | `common`, `uncommon`, `rare`, `epic` | `common` | Цвет имени во всплывающей подсказке |
| `maxSize` | нет | от 1 до 64 | `64` | Размер стопки |
| `drops` | нет | список дропа | роняет себя | Что даёт ломание |

**Метаданные постоянны.** Занятое вариантом число записывается в каждый сохранённый мир, где этот вариант есть. Перенумеровать или переставить варианты позже — значит превратить уже поставленные блоки во что-то другое. Добавляйте новые варианты в конец и никогда не переиспользуйте число.

Блок `basic` вмещает шестнадцать вариантов, `slab` — восемь. У `log` и `leaves` их четыре: флагам оси и опадания нужны собственные биты. Односостоянийные типы вмещают один.

## Модели, blockstates и текстуры

Описание блока или предмета его регистрирует. То, как он *выглядит*, — это по-прежнему обычный набор файлов ресурсов, в тех же папках и того же формата, которые Minecraft уже использует, но в вашем пространстве имён.

```
assets/mypack/blockstates/ruby_ore.json
assets/mypack/models/block/ruby_ore.json
assets/mypack/models/item/ruby/ruby.json
assets/mypack/textures/blocks/ruby_ore.png
assets/mypack/lang/en_us.lang
```

### Как называются варианты

Каждый блок с более чем одним вариантом получает свойство `blocks`, а его значениями становятся имена вариантов из описания. Поэтому файлу блока, регистрирующему `ruby_ore` и `deep_ruby_ore`, нужен blockstate с этими двумя вариантами:

```json
{
  "variants": {
    "blocks=ruby_ore": { "model": "mypack:ruby_ore" },
    "blocks=deep_ruby_ore": { "model": "mypack:deep_ruby_ore" }
  }
}
```

Блок с единственным вариантом и без других свойств использует вместо этого `normal`.

Там, где у блока есть собственные свойства, они соединяются запятыми в том порядке, в котором их перечисляет состояние: `blocks=ruby_log,axis=y`, `blocks=ruby_slab,half=bottom`, `blocks=ruby_stairs,facing=east,half=bottom,shape=straight`. Два свойства опущены намеренно: собственное свойство варианта у стены и `check_decay` с `decayable` у листвы — листве достаточно `blocks=ruby_leaves`.

### Модели предметов

По умолчанию предмет использует то, что blockstate даёт этому варианту — больше ничего не нужно. Указание `"itemModel": "item"` на блоке заставляет его искать собственный файл, в `models/item/<block>/<variant>.json`.

У предметов всегда второй вариант, потому что у каждого предмета пака есть подтипы:

```
assets/mypack/models/item/ruby/ruby.json
assets/mypack/models/item/ruby/polished_ruby.json
```

Путь — это registry name предмета, а затем имя варианта.

Жидкостям модель не нужна вовсе: она создаётся из текстур `still` и `flow`.

### Ловушки, о которых стоит знать

**Blockstate, называющий голую ванильную модель, наследует и ванильные текстуры.** `normal_torch`, `ladder`, `wooden_door_*` и `wheat_stage*` несут собственные текстуры, поэтому блок, указывающий на любую из них, получит ванильный вид, что бы вы ни написали в blockstate. Родительские модели вроде `cube_all`, `cross` и `block/crop` берут текстуры из blockstate и ведут себя нормально.

**`forge_marker: 1` не поддерживает multipart.** Blockstate для лозы должен быть обычным ванильным multipart, с текстурами, запечёнными в модель, а не переданными в неё.

**Имена берутся из языкового файла.** Блок или предмет показывает сырой ключ, пока `lang/en_us.lang` не даст ему имя, в обычной форме `tile.mypack:ruby_ore.name=Ruby Ore`.

## Как заставить ваниль обращаться с вашим блоком правильно

Ваниль проверяет свои блоки по тождеству в десятке мест, и блок пака, который очевидно должен работать, часто не работает. Это покрывают два ключа.

```json
{
  "material": "ground",
  "plantTypes": ["Plains", "Crop"],
  "behavesAs": ["till", "path"],
  "variants": { "ruby_grass": { "meta": 0, "hardness": 0.6 } }
}
```

**`plantTypes`** перечисляет типы растений Forge, которые ваш блок поддерживает, чтобы на нём можно было сажать саженцы, посевы и цветы.

**`behavesAs`** заставляет ваниль относиться к вашему блоку как к одному из своих:

| Значение | Что делает |
| --- | --- |
| `till` | Тяпка превращает его в грядку |
| `path` | Лопата превращает его в тропинку |

| `eat` | food | boolean | `false` | Использует анимацию еды |
| `alwaysEdible` | food | boolean | `false` | Можно съесть при полной шкале голода |
| `useDuration` | нет | int, тики | `32` | Сколько длится использование |

## Варианты сущностей

Файл в `assets/<modid>/entities/` делает новую сущность из уже существующей. Это полноценная сущность сама по себе: собственное registry name, собственное имя в мире, собственное яйцо призыва и собственная таблица лута, если вы её дадите, — построенная на поведении другой сущности, а не заменяющая её. В самой копируемой сущности не меняется ничего.

```json
    "attackDamage": 4

  "spawns": [

}
```

`scale` меняет и модель, и область попадания с обеих сторон: во что целитесь, в то и попадаете. Существо, само меняющее размер, — подрастающее животное или зомби-ребёнок, — масштабируется вокруг собственного выбранного размера, так что одно другому не мешает. `angryScale` раздувает её, пока есть цель, и возвращает к `scale`, когда цель теряется. Поскольку клиенту никогда не сообщают, за кем существо охотится, эту новость переносит флаг спринта: он ставится на варианте, использующем `angryScale`, и больше ни на чём, поэтому мод, читающий спринт у ваших вариантов, увидит, как он меняется. Вырасти под низким потолком возможно так же, как это возможно для растущего слизня, поэтому держите разницу умеренной.

Вариант роняет то же, что и копируемая сущность, потому что таблица лута зашита в код той сущности, а не ищется по имени. `lootTable` указывает на вашу собственную таблицу, которую вы затем кладёте в `loot_tables/entities/<name>.json`, как любую другую.

`texture` подставляется вместо той, которую сущность использовала бы обычно, при любом унаследованном рендерере, так что работает и с модовыми сущностями, и с ванильными. Она должна подходить модели, на которой отрисовывается, потому что модель — базовой сущности: это шкура, а не новая форма. Слои сохраняют собственные текстуры, поэтому броня на перекрашенном зомби по-прежнему выглядит бронёй.

Броню отрисовывают только у сущности, чей рендерер имеет слой брони. В этой версии это человекоподобные мобы и жители. Вариант коровы или паука может носить броню и получает её защиту, но её никто не рисует, так что `armor` внутри `attributes` — обычно более опрятный способ сделать такое существо крепким. `hideArmor` — для другого случая. Это человекоподобный, которому броня нужна в слотах ради защиты или ради читающего их мода, но видна быть не должна.

`hostile` заодно убирает поведение, заставлявшее существо убегать. Животное, избегавшее игроков или паниковавшее от ран, став враждебным, не делает ни того, ни другого — иначе оно бежало бы от того, кого должно атаковать. Нужна сущность, ходящая по земле, потому что используется то же поведение атаки, которое ваниль даёт своим мобам. Летающая или плавающая основа отмечается в логе и остаётся нетронутой. `passive` работает шире, но достаёт только до поведения, построенного по-ванильному. Мод, чья враждебность вписана в собственный тик или код урона, паку не переубедить.

Вариант — это собственный класс. Мир, где он есть, зависит от создавшего его пака ровно так же, как зависит от мода. Уберите файл — и существа в том мире уйдут вместе с ним.

## Участки деревень

Файл в `assets/<modid>/villages/` добавляет постройку, которую деревни могут возводить наряду с ванильными. Два вида, выбираются через `type`.

`farm` — это ванильное поле, но описанное, а не запрограммированное. Участок нужного вам размера, обрамлённый блоком. Внутри — ряды почвы, разделённые водными каналами, засаженные культурой из вашего списка, по выбору на каждый блок.

```json
{
  "type": "farm",
  "weight": 3,
  "width": 7,
  "depth": 9,
  "crops": ["simplecorn:corn"],
  "edge": "minecraft:log",
  "water": true,
  "rowWidth": 2
}
```

`template` вместо этого ставит одну из ваших структур `.nbt`, повёрнутую лицом к деревенской дороге.

```json
{
  "type": "template",
  "weight": 2,
  "width": 9,
  "height": 6,
  "depth": 9,
  "structure": "mypack:blacksmith_shed"
}
```

| Ключ | Для чего | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `type` | все | `farm` или `template` | `farm` | Какой это вид участка |
| `weight` | все | int | `3` | Насколько часто выбирается против других участков пака |
| `leastCount` | все | int | `1` | Наименьшее число на деревню, до прибавки за размер деревни |
| `mostCount` | все | int | `4` | Наибольшее число на деревню, до прибавки за размер деревни |
| `width` | все | int | `7` | Размер поперёк дороги |
| `height` | все | int | `4` | Высота расчистки над землёй |
| `depth` | все | int | `9` | Размер от дороги вглубь |
| `crops` | farm | список имён блоков | пшеница | Сажается по одной на блок, на случайной стадии роста |
| `edge` | farm | имя блока | `minecraft:log` | Рамка вокруг участка |
| `soil` | farm | имя блока | `minecraft:farmland` | Из чего сделаны ряды |
| `water` | farm | boolean | `true` | Провести водный канал между рядами |
| `rowWidth` | farm | int | `2` | Насколько широк каждый ряд почвы |
| `structure` | template | `namespace:name` | нет | Шаблон, который ставится |
| `integrity` | template | от 1 до 100 | `100` | Доля блоков шаблона, которые появятся, в процентах |
| `villagers` | все | int | `0` | Сколько людей порождает участок |
| `villagerEntity` | все | `namespace:name` | житель | Кто там живёт, например ваш собственный вариант сущности |
| `villagerX` | все | int | `1` | Где они появляются, поперёк участка |
| `villagerY` | все | int | `1` | Где они появляются, над полом |
| `villagerZ` | все | int | `1` | Где они появляются, вглубь участка |
| `ground` | все | имя блока | `minecraft:dirt` | Чем подбивается снизу на склоне |
| `requires` | все | список id модов или пространств имён паков | нет | Участок опускается, если присутствует не всё |

Каждый участок пака предлагается деревням как одна запись. `weight` решает, какой из ваших участков выберут, когда деревня попросит. Какой участок использовался при установке, записывается в собственные данные деревни, и при загрузке она перестраивается верно.

## Биомы

`biomes/*.json`

```json
{
  "name": "Ruby Forest",
  "type": ["FOREST", "DENSE"],
  "temperature": 0.7,
  "rainfall": 0.8,
  "baseHeight": 0.15,
  "heightVariation": 0.25,
  "topBlock": "mypack:ruby_grass",
  "fillerBlock": "minecraft:dirt",
  "waterColor": "8040A0",
  "placement": { "climate": "warm", "weight": 8, "villages": true },
  "spawns": [
    { "entity": "minecraft:sheep", "type": "creature", "weight": 12, "min": 2, "max": 4 }
  ],
  "spawnRates": { "surfaceNight": 0.5, "undergroundDay": 2.0 }
}
```

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `name` | нет | строка | имя файла | Имя, показываемое игроку |
| `id` | нет | int | назначается за вас | Фиксированный id биома. Задавайте, только если нужна стабильность |
| `type` | нет | список типов словаря | нет | Например `FOREST`, `COLD`, `NETHER` |
| `temperature` | нет | float | `0.5` | Ниже 0.15 идёт снег, выше 1.0 — жара пустыни |
| `rainfall` | нет | float, от 0 до 1 | `0.5` | Насколько влажно |
| `rain` | нет | boolean | `true` | Бывает ли погода вообще |
| `snow` | нет | boolean | `false` | Выпадает ли дождь снегом |
| `baseHeight` | нет | float | `0.1` | Высота рельефа. Уровень моря 0, равнины 0.125 |
| `heightVariation` | нет | float | `0.2` | Насколько холмисто |
| `topBlock` | нет | имя блока | трава | Поверхностный блок |
| `fillerBlock` | нет | имя блока | земля | Сразу под поверхностью |
| `stoneBlock` | нет | имя блока | камень | Основная толща грунта |
| `types` | нет | список типов словаря | нет | Регистрирует биом под ними, например `FOREST` или `WET`, чтобы другие моды его находили |
| `waterColor` | нет | hex-цвет | `FFFFFF` | Оттенок воды |
| `baseBiome` | нет | имя биома | нет | Существующий биом, у которого копируются настройки |
| `decoration` | нет | объект | ванильные значения | Количества на чанк для деревьев, травы, цветов, тростника, кактусов, озёр, глины и прочего |
| `spawns` | нет | список объектов | ванильный список | См. ниже |
| `keepDefaultSpawns` | нет | boolean | `false` | Сохранить ванильный список наряду с вашим |
| `spawnChance` | нет | float, меньше 1 | `0.1` | Насколько вероятно, что при первом создании земли будет поставлено ещё одно стадо. Игра бросает кубик, пока он выпадает удачно, поэтому 1 не останавливается никогда и заполняет мир, пока не кончится место. Всё от 0.99 и выше отвергается, и берётся 0.99 |
| `spawnRates` | нет | объект `surfaceDay`, `surfaceNight`, `undergroundDay`, `undergroundNight` к множителю | нет | Как часто здесь появляются враждебные мобы, вместо глобальных настроек. См. ниже |
| `placement` | нет | объект |, | Где генерируется. См. ниже |
| `requires` | нет | список id модов или пространств имён паков | нет | Файл пропускается, если присутствует не всё |

Запись спавна принимает `entity` (обязателен), `type` (`creature`, один из [типов существ](#списки-значений)), `weight` (`10`), `min` (`1`) и `max` (`min`).

`spawnRates` касается только враждебных мобов и ничего больше. Он принимает четыре ключа и никаких других: `surfaceDay` и `surfaceNight` для мест, где видно небо, `undergroundDay` и `undergroundNight` для мест, где не видно. Каждый — множитель того, как часто враждебному мобу позволено появиться: `1` — обычная частота, `0` останавливает их полностью, меньше 1 отклоняет часть попыток, а больше 1 пропускает попытки, которые игра иначе отвергла бы, так что `2` — это вдвое больше. Пропущенный ключ означает, что биом не решает, и используется глобальная настройка для этого времени и места. Всё прочее, написанное здесь, ключом не является и игнорируется, поэтому частота, названная по типу существа, не делает ничего.

`placement`:

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `climate` | нет | строка | нет | В какую ванильную климатическую группу входит |
| `weight` | нет | int | `10` | Насколько часто выбирается против соседей |
| `villages` | нет | boolean | `false` | Могут ли генерироваться деревни |
| `villageSpawn` | нет | boolean | `true` | Могут ли в них появляться жители |
| `strongholds` | нет | boolean | `false` | Могут ли генерироваться крепости |
| `playerSpawn` | нет | boolean | `false` | Может ли здесь оказаться точка появления мира |

```json
{
  "id": 12,
  "suffix": "DIM_ruby",
  "keepLoaded": false,
  "terrain": { "type": "overworld", "structures": false },
  "biomes": { "source": "single", "biome": "mypack:ruby_forest" },
  "sky": {
    "skyColor": "3B1E4A",
    "fogColor": "20102A",
    "cloudHeight": 160,
    "hasSkyLight": true,
    "ambientLight": 0.1,
    "movementFactor": 4.0
  },
  "gameRules": { "doMobSpawning": "false" }
}
```

**Верхний уровень**

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `id` | да | int |, | Id измерения. Не должен конфликтовать с другим модом |
| `suffix` | нет | строка | `DIM_<name>` | Папка сохранения |

| `gameRules` | нет | объект | нет | Правила, действующие только здесь |
| `requires` | нет | список id модов или пространств имён паков | нет | Файл пропускается, если присутствует не всё |

**`terrain`**

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `type` | нет | `overworld`, `flat`, `void`, `nether`, `end` | `overworld` | Какой генератор его строит |
| `generatorOptions` | нет | строка | нет | Строка генератора, как у пресета суперплоского мира |

**`biomes`**

| Ключ | Обяз. | Значение | По умолчанию | Что делает |

| `spawning` | нет | boolean | `true` | Появляются ли мобы |

| `beds` | нет | boolean | `true` | Выключено — кровати взрываются |
| `waterVaporizes` | нет | boolean | `false` | Вода испаряется |
| `cloudHeight` | нет | int | `128` | На какой высоте облака |
| `cloudColor` | нет | hex-цвет | нет | Оттенок облаков |
| `groundLevel` | нет | int | `63` | Уровень моря, используется для горизонта и поиска точки появления |
| `movementFactor` | нет | float | `1.0` | Отношение расстояний к обычному миру. У Нижнего мира 8 |
| `fogColor` | нет | hex-цвет | нет | Оттенок тумана |
| `showFog` | нет | boolean | `false` | Густой туман, как в Нижнем мире |
| `skyColor` | нет | hex-цвет | нет | Оттенок неба |
| `fixedTime` | нет | int, тики | нет | Фиксирует время суток |
| `sunriseColors` | нет | boolean | `true` | Подкрашиваются ли рассвет и закат |

## Порталы и ворота

Блок `portal` несёт секцию `portal`:

```json
{
  "type": "portal",
  "material": "portal",
  "portal": {
    "dimension": 12,
    "returnDimension": 0,
    "gate": "mypack:ruby_gate",
    "cooldown": 60,
    "platform": true,
    "platformBlock": "mypack:ruby_block",
    "owned": true
  },
  "variants": { "ruby_portal": { "meta": 0, "hardness": -1, "light": 11 } }
}
```

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `dimension` | да | int |, | Куда он отправляет |
| `returnDimension` | нет | int | `0` | Куда отправляет обратно |
| `gate` | нет | имя ворот | нет | Ворота, которые должны быть открыты для прохода |
| `cooldown` | нет | int, тики | `60` | Через сколько тот же игрок может воспользоваться снова |
| `platform` | нет | boolean | `true` | Строить площадку приземления по прибытии |
| `platformBlock` | нет | имя блока | собственная рама портала | Из чего сделана эта площадка |
| `sound` | нет | имя звука | нет | Проигрывается при переходе |
| `owned` | нет | boolean | `true` | Пользоваться могут только тот, кто его построил, и те, кому он позволил. Такой портал ещё и не боится взрывов |

`gates/*.json`

```json
{
  "name": "The Ruby Gate",
  "scope": "player",
  "dimension": 12,
  "open": false,
  "unlock": { "consume": "mypack:ruby", "consumeCount": 4, "killed": "minecraft:wither" },
  "unlockedMessage": "%dim% is now open",
  "blockedMessage": "You need %item% to enter %dim%",
  "safeReturn": true
}
```

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `dimension` | да | int |, | Измерение, которое они охраняют |
| `name` | нет | строка | имя файла | Показывается игроку |
| `scope` | нет | `player`, `global` | `player` | По одному игроку или на весь мир сразу |
| `open` | нет | boolean | `false` | Открыты ли изначально |
| `unlock` | нет | объект |, | Что их открывает. См. ниже |
| `unlockedMessage` | нет | строка | `%dim% is now open` | Показывается при открытии |
| `blockedMessage` | нет | строка | `You need %item% to enter %dim%` | Показывается при отказе |
| `safeReturn` | нет | boolean | `false` | Заблокированное возвращение всё равно приводит в безопасное место, а не отказывает |
| `portalBlocks` | нет | список имён блоков | все порталы | Ограничивает ворота этими блоками портала, чтобы у одного измерения могла быть и охраняемая дверь, и открытая |

`unlock` принимает `hold` (предмет, который надо держать), `consume` вместе с `consumeCount` (`1`), `craft` (предмет, который должен быть скрафчен), `advancement` и `killed` (имя сущности: ворота открываются тому, кто её убьёт, поэтому ключом от мира может владеть босс) вместе с `killedCount` (`1`), когда одного мало, — счёт ведётся по игроку или на весь мир, как скажет `scope`. Добавление `killedDrops` (имя предмета) заставляет засчитанные убийства класть этот предмет к ногам победителя вместо открытия ворот и начинает счёт заново, поэтому ключ можно заработать снова и передать тому, кто за него не сражался; поставьте ворота на `hold` или `consume` того же предмета, чтобы сделать его ключом. `%item%`, `%mob%` и `%dim%` подставляются за вас. Ключу, который роняет моб, здесь ничего особенного не нужно: дайте мобу дроп и поставьте ворота на `hold` или `consume`.

## Шаблоны мира

`worldtemplates/*.json` собирает форму мира в один файл, поэтому пак поставляет целый мир разом, а не просит игрока выставить дюжину настроек конфига.

```json
{
  "name": "Ruby World",
  "default": "void",
  "dimensions": [0],
  "settings": {
    "voidWorld": true,
    "flatBedrock": true,
    "blockBiomes": true
  },
  "structures": {
    "villages": false,
    "mineshafts": false,
    "strongholds": true
  },
  "roles": { "ocean": "mypack:ruby_ocean" }
}
```

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `name` | нет | строка | имя файла | Показывается в логе и в отчётах |
| `default` | нет | имя биома или `void` | `void` | Чем заполняется биом, убранный блокировкой |
| `roles` | нет | объект «роль к биому» | нет | Биомы, занимающие определённые роли, например океан или река |
| `structures` | нет | объект «[имя структуры](#списки-значений) к boolean» | нет | Ванильные структуры, включённые или выключенные |
| `settings` | нет | объект | нет | Значения конфига, которые задаёт шаблон |
| `dimensions` | нет | список целых | все измерения | К каким измерениям применяется |

`settings` использует те же имена ключей, что и конфиг, поэтому никакой таблицы соответствий учить не надо.

Какой шаблон активен, решает настройка конфига `worldTemplate`. Оставленная как `auto`, она отдаёт победу паку с наивысшим приоритетом из тех, что несут шаблон, — в том же порядке, которому следует всё остальное. Названный там шаблон выбирается напрямую.

## Вступление к миру

`worldintro/*.json` показывает набор страниц, когда игрок входит в мир, до того как он получит управление. Бегущий текст поверх картинки, титульная карточка, слайдшоу или всё это подряд.

```json
{
  "once": true,
  "music": "minecraft:music.credits",
  "pages": [
    {
      "background": "mypack:textures/gui/sunrise.png",
      "text": "mypack:texts/opening.txt",
      "mode": "scroll",
      "time": 14.0,
      "direction": "up",
      "textScale": 3.0,
      "settle": true
    },
    {
      "backgrounds": [
        "mypack:textures/gui/logo_a.png",
        "mypack:textures/gui/logo_b.png"
      ],
      "interval": 4.0,
      "text": "mypack:texts/title.txt",
      "mode": "static",
      "textScale": 2.0
    }
  ]
}
```

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `pages` | да | список страниц | нет | Показываются по порядку. Файл без страниц отвергается с ошибкой |
| `once` | нет | boolean | `false` | Играть один раз на игрока на мир, а не при каждом входе |
| `music` | нет | имя звукового события | нет | Одна дорожка на весь показ, запускается с первой страницей |
| `requires` | нет | список id модов или пространств имён паков | нет | Вступление пропускается, если присутствует не всё |

Каждая запись внутри `pages`:

| Ключ | Обяз. | Значение | По умолчанию | Что делает |
| --- | --- | --- | --- | --- |
| `mode` | нет | `scroll` или `static` | `scroll` | Текст, который движется, или текст, который стоит, пока игрок не пойдёт дальше |
| `text` | нет | путь к файлу `.txt` | нет | Слова. Не пишите его для страницы из одних картинок |
| `background` | нет | путь к текстуре | плиточный земляной фон | Один фон |
| `backgrounds` | нет | список путей к текстурам | нет | Несколько, по кругу. Добавляется к `background`, если задано и то и другое |
| `interval` | нет | секунды | `5.0` | Сколько держится каждый фон, когда их больше одного |
| `time` | нет | секунды | вычисляется из текста | Сколько длится бегущая страница от начала до конца |
| `direction` | нет | `up` или `down` | `up` | В какую сторону едет текст |
| `textScale` | нет | число | `1.0` | Умножает размер шрифта |
| `settle` | нет | boolean | `false` | Закончить с последней строкой по центру, а не уводя её за пределы экрана |

Текстовые файлы кладутся в `assets/<namespace>/texts/<name>.txt`. Обычный текст, по абзацу на строку, а пустые строки сохраняются пустыми. `PLAYERNAME` заменяется именем игрока — та же подстановка, что и в ванильной финальной поэме.

`time` задаёт, сколько длится страница, поэтому одна и та же страница занимает одно и то же время, держит она одну строку или двадцать. Скорость чтения настраивайте тем, сколько вы на страницу положите. Не пишите `time` — и страница пойдёт с той же скоростью, что ванильные титры, где больше текста просто дольше едет.

Бегущая страница переходит к следующей, когда её время вышло. Последняя страница сама не переходит никогда, она ждёт. Внизу расположены **Next Page** и **Skip All** либо единственная **Continue to World** на последней странице. Escape делает то же, что Skip All. Статические страницы центрируют каждую строку. Бегущие держатся фиксированной колонки, как титры.

В одиночной игре мир за вступлением ставится на паузу, чтобы к игроку ничего не подкралось, пока он читает. На сервере мир продолжает идти, а ванильный клиент вступления не видит вовсе и входит как обычно.

`once` запоминается в сохранённых данных игрока и переживает смерть. `/rdplserver intro` сбрасывает его тому, кто выполнил команду, поэтому вступление сыграет снова при следующем входе. На месте оно не повторяется, и это не даёт использовать его как лазейку обратно во входную последовательность посреди игры.

Фоны растягиваются на всё окно, поэтому изображение 16:9 подходит окну 16:9, а квадратное выглядит сплющенным. Обрезайте картинку по форме, а не полагайтесь на подгонку. `music` принимает любое зарегистрированное звуковое событие — ванильное или добавленное вашим паком через `sounds`. Оно не зациклено, поэтому короткая дорожка доиграет и оставит после себя тишину.

Если вступление несут несколько паков, их страницы идут подряд в порядке паков, а не побеждает одно. Ограничьте их через `requires`, если нужно только одно.

## Игровые правила

`gamerules/*.json`

```json
{
  "0": {
    "doFireTick": "false",
    "keepInventory": "true",
    "randomTickSpeed": "3"
  },
  "-1": {
    "doFireTick": "true"
  }
}
```

Каждый ключ — это id мира, которому принадлежат правила: `0` для обычного мира, `-1` для Нижнего, `1` для Края и то, что мод использует для своего. Значения — строки, как в команде `/gamerule`, поэтому `"false"`, а не `false`. Они применяются к новым мирам. Файл измерения несёт те же правила в блоке `gameRules`, и они действуют только в этом мире.
